## Важливе

### В1. «Жорсткий» денний ліміт не жорсткий: паралельні фото й втрачений облік
- **Де:** `phase-3.md` §4 «Альбом: кожне фото — окремий прийом і виклик» (рядок 72), «Крок 0» (74), `[П] Облік витрат` (196); `decisions.md`: «перевищення — не більше одного виклику».
- **Сценарій:** `aiSpendToday` = 290 000 µUSD (ліміт 300 000). Надсилаю альбом із 10 фото → 10 апдейтів із різними `update_id`, кожен у своєму `ctx.waitUntil`; усі 10 читають суму **до того, як хоч один запише `ai_usage`** → усі проходять перевірку → ≈ +100 000…210 000 µ, разом ≈ 390–500 тис. при ліміті 300 тис. Твердження «не більше одного виклику» хибне саме для альбому, який спека допускає. Друга діра — рядок 196: Worker, убитий після платної відповіді, але до `recordAiUsage`, → витрата невидима (`markUpdateProcessed` уже стоїть, повтору немає, `src/app.ts:74`).
- **Виправлення:** **резервування замість перевірки-потім-запису.** Крок 0 = один умовний `INSERT INTO ai_usage (… cost_micro = FOOD_CALL_EST_MICRO, purpose='food_photo', reserved=1) SELECT … WHERE (SELECT COALESCE(SUM(cost_micro),0) FROM ai_usage WHERE user_id=? AND local_date=?) + FOOD_CALL_EST_MICRO <= AI_DAILY_LIMIT_MICRO`; 0 змін → текст ліміту, клієнта не викликано. Після відповіді — `UPDATE` того ж рядка фактичною ціною (`usage`); при 4xx/5xx без оплати — `DELETE` резервування. Таймаут тоді не потребує окремого правила (рядок уже лежить з оцінкою), а вбитий Worker лишає оцінку замість нуля. Один атомарний оператор D1 серіалізує паралельні фото. Тест: 10 паралельних при залишку на 2 → клієнт викликано ≤ 2 (мутант: перевірка без резервування → червоний). Формулювання `decisions.md` виправити.

### В2. `thinking` не передаємо ≠ «без thinking»: на Sonnet 5.5 це adaptive-мислення
- **Де:** §4 «`thinking` не передаємо (глибина — `effort: low`)», §5 «вихід 400–700 токенів».
- **Доказ:** skill `claude-api` (таблиця Thinking & Effort): Claude Sonnet 5.5, *Omitting `thinking` → Runs **adaptive***; `{type:"disabled"}` → 400; вимкнути можна лише `{type:"between_tools"}` (ефорт ≤ high, без інших полів). Токени мислення біляться як вихідні й **їдять `max_tokens 1500`**.
- **Сценарій:** тарілка з 6 позиціями: JSON ≈ 500–600 токенів + мислення на `low` (довжина не обмежена спекою) → `stop_reason: max_tokens` → INVALID (прийому немає) — і платно. Оцінка «типово ≈ $0,01» та 25 с дедлайн також не враховують мислення. Стеля $0,02 (1500 × $10/MTok + вхід) лишається, але ймовірність INVALID зростає.
- **Виправлення:** або явно `thinking: { type: "between_tools" }` + `effort: "low"` (детермінована ціна й затримка для задачі «розпізнай і заповни схему»), або лишити adaptive, але підняти `FOOD_MAX_TOKENS` (≈ 2500; стеля ≈ $0,03) і в таблиці 5 фото 3.3 записувати `usage.output_tokens`. Рекомендація — перше; 3.3 звіряє двома фото. Запис у `decisions.md`.

### В3. Прогалини профілю: спека суперечить сама собі, а запасний хід має побічний ефект на план
- **Де:** §3 «Коли рахувати й питати»: «питання екранами 1b … **Екрани 1b не годяться для одного кроку без проходу решти анкети** — запасний хід: список і `/profil` (**[П]**)»; P3.2.4: «**одне** питання про рік народження».
- **Докази:** `phase-1b.md:40`: у `/profil` лише перегляд і [🔄 Пройти знову] — анкета з Q1 до кроку `plan`; `src/domain/onboarding.ts:8` — послідовність `sex → birth → height → weight → meals → diet → sleep → activity → plan`; коміт `d7b5b03` (2.4): `onboarding.accept` скидає `training_days` при активації плану.
- **Сценарій:** анкета пропущена, `birth_year = NULL`. `/yizha` → за §3 екрани 1b «не годяться» → запасний хід: людина тисне [Пройти знову], проходить 12 екранів, а на кінці — новий план і **скинуті дні тренувань** — заради одного поля. P3.2.4 («одне питання») за такою схемою не здійснюване. 3.2 доведеться вигадувати дизайн самій, а це рішення, що зачіпає Фазу 1b/2.
- **Виправлення (закрити в спеці):** одне запитання = окреме повідомлення бота з **reply-маршрутом**, як у нагадування про вагу (Фаза 2, `weight.replyToReminder`; стан не потрібен, `onboarding_state` не чіпаємо): `goal`/`sex`/`activity` — кнопки з окремим префіксом `callback_data` (вільним: `o:`, `s:`, `p:`, `m:`, `n:` зайняті; напр. `f:`) з тими самими значеннями enum; `birth_year`/`height_cm`/`weight_kg` — текст у reply, валідація тими ж межами (1930–2020 / 120–230 / 30–300) із `domain/onboarding.ts`; пише наявна функція оновлення профілю в `repo.ts` (3.2 обирає). Додати в порядок маршрутизації тексту пункт (1б). Вилучити «екрани 1b не годяться» і [П]. P3.2.4 лишається.

### В4. Сид: невизначено, хто й як зіставляє українські назви з `fdc_ref`; дубль аліасів гаситься мовчки
- **Де:** §2 «`scripts/foods-map.json` (ручний список: `name_uk`, `aliases[]`, `fdc_ref`) … `INSERT … ON CONFLICT DO NOTHING`»; «назви й аліаси українською — наші».

Переклад — агент 3.1, звірку описів робить сам скрипт, людина дивиться таблицю.

## Дрібниці

- **Д1.** §4: «1280×960 = 1610 візуальних токенів». Для Sonnet 5.5 діє «Standard»-тир: макс. 1 568 токенів / 1 568 px (vision, 2026-11-20) — картинка буде зменшена, ≈ 1 568. Вплив на ціну ≈ 0; виправити число або прибрати.
- **Д2.** §4 «Разом … округлена один раз» (рядок 92) vs підтвердження: знімок округлюється **по позиціях** (рядок 95), `dayTotals` — сума знімків. Прев'ю «Разом: 520», після `[Вірно]` — 522 (до ±4 ккал на 8 позиціях). Одне правило: скрізь сума округлених позицій.
- **Д3.** §3: крайній, але дозволений профіль (ж, 30 кг, 120 см, 1930, `low`, `lose_fat`) дає `kcal = 450` (перерахував `node -e`), а `nutrition_targets.kcal` має CHECK 800–6000 → виняток у ледачому створенні при `/yizha`. Те саме зверху (м, 300 кг, 230 см). Потрібне правило: «поза 800–6000 — норму не рахуємо, текст "перевір профіль"».
- **Д4.** Повторне фото: `meals` зберігає `photo_file_id`, але не `file_unique_id`; та сама картинка вдруге = новий `update_id` = нова оплата. Дедуп за `update_id` захищає лише від повтору вебхука. Обмежено лімітом; потенційний борг: шукати `pending` із тим самим `file_unique_id` за 24 год.
- **Д5.** §4 «Таймаут … `ai_usage` — `FOOD_CALL_EST_MICRO`»: дедлайн може спрацювати на `getFile`/завантаженні, коли запиту до Anthropic ще не було → завищений облік до $0,015. Уточнити «лише якщо запит до Anthropic уже відправлено» (після В1 це природно).
- **Д6.** §4 `0 = вилучити позицію (решта номерів не змінюється)`: при наступному `[Грами]` нумерований список — за `position` (1, 3) чи за порядком (1, 2)? `parseGrams(text, n)` приймає n = лишилось. Визначити (рекомендація — за порядком показу).
- **Д7.** §4 список відомих назв «≤ 300»: порядок і відбір, коли каталог виросте (сид ≈ 100 + `ai_estimate`), не визначено; недетермінований список ламатиме кеш-міркування й тести. Правило: спершу `seed`, далі `ai_estimate` за кількістю використань.
- **Д8.** §6: `−100` при вуглеводах, що впираються в 0, лишає `kcal ≠ 4Б + 4В + 9Ж` (інваріант «арифметично цілісна норма», §3); і міграція 3.4 — `reminders_sent_kind` це **table-level CHECK** (`migrations/0005_reminders.sql:15`), тож «розширити CHECK» у SQLite = перебудова таблиці; спека має сказати це явно й дати 3.4 `backup` перед міграцією preview/prod.
