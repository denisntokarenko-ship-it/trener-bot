## Блокери

### Б1. `activatePlan` залишає активне тренування без дня (§2 `activatePlan`, §5, P2.7)
Спека не згадує тренування в статусі `active`. У коді `repo.getProgramDay(userId, code)` шукає день **лише в активній програмі за кодом** (`src/db/repo.ts:190–193`), а `workout-flow.ts:208, 416, 452` викликає його з `workout.dayCode`.
**Сценарій:** власник у залі (active-тренування дня `A`), у телефоні натискає [✅ Прийняти] → стара програма `active = 0`, нова має коди `FA/FB` → `getProgramDay(…, 'A')` = `null`. Тренування не продовжити, а `workouts_one_active` не дає почати нове до `abandonStale` (4 год). Історія цілісна, але бот «зависає» для користувача.
**Що написати в спеку:** або `activatePlan` відмовляє («Заверши або скасуй поточне тренування»), або в тому ж батчі закриває `active` як `abandoned`; плюс історія в §8 («Given active-тренування, When [✅], Then …») і тест у 1b.1/1b.2. Те саме для старту анкети посеред тренування.

### Б2. `EMPTY_DAY` — досяжний тупик без екрана й переходу (§3 «Result», §5)
Спека повертає `EMPTY_DAY` (< 3 слотів), але ні в §1, ні в §5 немає, що бачить людина й куди йти. Я змоделював правила §3 (патерни дня × `place`/`min_level`/`stress`/N) для всіх комбінацій місце × рівень × дні × `session_min` × підмножина обмежень × 3 варіанти: **293 комбінації дають хоч один день < 3 слотів**, зокрема побутові:
- `gym`, новачок, 3 дні, 30 хв, обмеження «плечі» → «Все тіло A»: squat, ~~hpush~~, vpull, ~~vpush~~ = 2 слоти (усі `hpush`/`vpush` каталогу мають `stress ∋ shoulder`);
- `home` + «коліна» чи «спина» чи «зап'ястя» на 30 хв (4 слоти) → те саме.
**Сценарій:** людина з болем у плечі проходить 14 питань і отримує помилку, яку спека не описує; `[✅ Прийняти]` нема, `[✏️ Змінити дні]` не допоможе (день усе одно порожній).
**Що написати:** екран «Не вдалося скласти план з такими обмеженнями» + дії (зняти обмеження / збільшити тривалість / [🔄 Спочатку]); історія P2.x з вхідом «gym, novice, 3d, 30 хв, shoulder → EMPTY_DAY → екран, нічого не записано». І/або скоротити поріг (≥ 2 слоти) чи додати ізометричні/без-плечові `hpush`-вправи — рішення за автором, але стан має бути закритий.

## Важливе

### В1. Генератор не повністю детермінований словами (§3, «Добір вправи», «Підходи», таблиця цілей)
Місця, де двоє виконавців напишуть різне, а тест спеки (P2.2/P2.3) це не зловить:
1. «пропускаючи вжитих у цьому дні» — у який бік? Наступний за колом, чи далі лише `idx+1` без обгортки? Я брав «за колом»; результат залежить.
2. «+1 compound» (`muscle`, `strength` для `mid`/`adv`) — +1 **підхід** чи +1 **слот**? Із «Невідомого» («+1 підхід для `mid`») випливає перше, але таблиця цілей це не каже.
3. `strength`: «accessory ≤ 2 на день» — які саме лишаються? (за порядком патернів?) і чи рахується `core`.
4. `lose_fat`: «+1 слот `core`, якщо слотів ≥ 6» — понад ліміт N чи в його межах? Для 60 хв (N=6) вийде 7?
5. Яка кількість «слотів ≥ 6» — до чи після обрізання N і `EMPTY_DAY`?
**Що зробити:** додати у спеку один повністю розписаний приклад (профіль → план по слотах, `id`, підходи × повтори) для 2 цілей — як золотий тест для 1b.1.

### В2. Стартові ваги губляться тихо: якорі ≠ вправи плану (§1 Q7, §2, §3 «Добір»)
Q7 питає 4 якорі (`gym`: присідання зі штангою, жим лежачи, тяга блока, жим гантелей сидячи), але план обирає вправу `(n + variant) mod len`. У моделюванні для `gym`/novice: variant 0 містить усі 4 якорі, **variant 1 — лише тягу блока (1 із 4)**, variant 2 — 2 із 4. Додатково якорі виключаються ціллю й обмеженнями: `health` (без штанги), «коліна» (id 1), «плечі» (id 2, 4). Людина ввела «60×8» — а в плані інша вправа, і запис мовчки не використано (спека: «застосовуються до слотів, чия вправа має запис»).
**Сценарій:** новачок вводить жим 60×8, натискає [🔁 Інший варіант] → жим гантелей на похилій/тренажер, старт знову `min_weight_kg`; жодного повідомлення.
**Варіанти:** питати ваги після підтвердження плану для вправ **фактичного** плану; або мапити вагу на патерн (`hpush` → перша вправа патерну, з коефіцієнтом/калібруванням); мінімум — сказати людині «ваги застосуються лише до вправ плану» і додати історію.

### В3. «Все тіло A» і «Все тіло B» майже однакові; цикл варіантів схлопується (§3)
Для `gym`/novice/variant 0: A = {1,2,3,4,5,6,23}, B = {6,1,8,2,5,3,23} — **6 із 7 вправ спільні**, різниця лише `vpush` ↔ `hpull`. Старі A/B власника були різні (A: присідання/жим/тяга/жим плечей; B: РТ/жим ногами/тяга/тренажер/ноги у висі). Для `home` кандидатів у патерні по 2, тож варіанти 0 і 2 збігаються: людині показують лише 2 різні плани, а P2.2 («різні variant — різні вправи хоча б в одному слоті») хибна для пари (0,2); P2.8 «4-й = 1-й» формально ок, але «Інший варіант» → той самий план.
**Що зробити:** зсув добору залежить від дня (`n + variant + dayIndex`), перевірка «усі 3 варіанти різні» лише там, де кандидатів ≥ 3; для `home` розширити каталог (напр. `hpull`, `squat`) або чесно сказати «варіантів 2».

### В4. Два споживачі тексту: анкета й `await_input` тренування (§1 «Потік»)
У коді `workouts.await_input` очікує вагу текстом, а `bot.ts:32` скидає його на будь-якій команді. Спека: «Текст приймається лише на кроці, що чекає текст», але не каже, хто виграє, коли водночас є `onboarding_state.step = height` і `awaitInput` активного тренування.
**Сценарій:** анкета на кроці «Зріст», власник відкриває /trening, тисне [⚖️ Вага], пише «80» → число йде в `height` (відхилено 120–230) чи у вагу підходу? Або навпаки.
**Що написати:** пріоритет (напр. `awaitInput` тренування > анкета; команда скидає обидва очікування) і історію.

### В5. Існуючий сид не оновлює `video_url` (§9, 1b.1)
`scripts/seed-core.ts:134–138`: `INSERT … video_url = NULL … ON CONFLICT DO UPDATE SET …` — `video_url` **не в списку SET**, а в VALUES завжди `NULL`. Спека каже «правка — оновити сид (upsert за slug)» і «заповнює 1b.1 для всіх 30». Для існуючих 18 вправ у проді відео ніколи не з'явиться, поки `DO UPDATE` не розширять; для тесту «усі мають URL» на свіжій БД це не видно.
**Додати:** явний пункт у 1b.1 («`video_url = excluded.video_url` у `DO UPDATE`; NULL у сиді не перетирає вже заповнене» — вибрати політику) і тест на повторний сид з `video_url`.

### В6. Дві суперечливі формулювання про стартові ваги (§2)
«`activatePlan`… Стартові ваги застосовуються до слотів, чия вправа має запис» (слоти не мають колонки ваги; `activatePlan` — 1b.1) і «`start_weights` читає repo, не домен» (`nextPrescription(…, start)` — 1b.2, правило 1). Плюс P1.7 пише `start_weights` одразу при відповіді, а §5 каже «до [✅] нічого не пишеться» (про `programs`; але `start_weights` уже працює для **старої** програми).
**Прояснити:** `activatePlan` стартові ваги не «застосовує» — вони живуть у `start_weights` і підставляються лише в правилі 1 без історії. Прибрати «застосовуються до слотів». Додати: чи питати вагу вправи, у якої вже є історія (власник!), чи показувати «є історія — пропущено».

### В7. Анкета «Пройти знову» під-визначена (§1 «Потік», `/profil`)

**Що написати:** або чернетка (відповіді в `onboarding_state`/чернетку, у `user_profiles` лише при [✅]), або явний рядок «план збудовано за ціллю X» у `/profil` і правила Q1 при повторі.
