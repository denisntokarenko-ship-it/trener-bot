## Важливе

### В1. Пропозиція-сирота: `pending` без кнопок блокує предмет на 48 год
- **Де:** `phase-4.md` §5 (рядок 85): «пропозиції, створені до збою, лишаються `pending` (кнопок немає, спливуть за 48 год)»; §1 (рядок 25): частковий `UNIQUE (user_id, subject_key) WHERE status='pending'`; §2 (рядок 52): «другий `pending` на той самий `subject_key` — відмова».
- **Сценарій:** «заміни присід на жим ногами» → у циклі модель викликає `propose_change` (рядок `pending` створено) → другий запит до API таймаутиться на 25-й секунді → «Не встиг відповісти. Спробуй ще раз», кнопок немає. Користувач повторює → модель знову `propose_change` → `is_error: «вже є така пропозиція»` → модель пише «вже запропоновано, підтверди кнопкою», **кнопки немає ніде**, а пропозиція прив'язана до слота 48 год і займає 1 з 3 місць `PROPOSALS_PENDING_MAX`. Вийти можна лише чекати.
- **Виправлення:** або (а) при збої/таймауті ходу код ставить пропозиціям цього ходу `status = 'expired'` (`createProposal` повертає id, ходу вони відомі); або (б) конфлікт `subject_key` повертає **наявну** пропозицію, і код надсилає її картку з кнопками (для `message_id` NULL). Краще обидва. Тест: таймаут після `propose_change` → 0 відкритих; повтор → картка є.

### В2. `chatInFlight` + резервування — не атомарні (той самий клас, що В1 рев'ю 3.0)
- **Де:** §1 (рядок 31) `chatInFlight(userId, now)` = читання `ai_usage`; §5 конвеєр (рядок 83): «(1) перевірки розділу 4 → (2) `reserveAiUsage`». `src/db/repo.ts:1168` `reserveAiUsage` має лише предикат суми — предиката «немає свіжого чату» немає.
- **Сценарій:** користувач надсилає два повідомлення поспіль (звична поведінка в Telegram). Два апдейти з різними `update_id` обробляються в окремих `waitUntil`; обидва читають `chatInFlight` до того, як будь-який вставив резервування → обидва проходять → два паралельні цикли, дві відповіді вперемішку, обидва пишуть `chat_turns`. P4.2.3 перевіряє лише послідовний випадок (резервування < 30 с тому).
- **Виправлення:** перенести умову в сам `INSERT … SELECT … WHERE` резервування (`AND NOT EXISTS (SELECT 1 FROM ai_usage WHERE user_id=… AND purpose='chat' AND input_tokens=0 AND output_tokens=0 AND created_at > ?)`) — `reserveAiUsage` отримує необов'язковий параметр `exclusiveWithin`; 0 змін = «Ще відповідаю» (а не «ліміт»: причину з'ясовує код другим читанням). Тест: два паралельні `reserve` → один рядок.

### В3. Помилка API на 2-й ітерації стирає вже оплачену 1-шу (`release` замість `settle`)
- **Де:** §5 (рядок 85): «HTTP-помилка API (4xx/5xx) або дедлайн **до першого запиту** → `releaseAiUsage`»; реалізація, яку перевикористають: `src/ai/food-prompt.ts:88–95` `classifyAiError` повертає `refund: true` для **будь-якого** HTTP-статусу, а `src/bot/meal-flow.ts:196` робить `release()`; `src/db/repo.ts:1193` видаляє рядок з токенами 0/0.
- **Сценарій:** ітерація 1: 4 000 вхідних токенів, `tool_use`, оплачено → інструмент виконано → ітерація 2: HTTP 529/429 → `refund: true` → рядок резервування видалено, 1-ша оплачена ітерація (≈ $0,0004) зникає з `aiSpendToday`. Систематично під навантаженням API ліміт недооцінює витрати; «жорсткий» ліміт знову не жорсткий.
- **Виправлення:** правило «release лише якщо жодна відповідь ще не отримана; інакше `settle` накопиченою сумою (≥ 1 вхідного токена)». Для 5xx/429 без відповіді на 1-му запиті — release як у Фазі 3. Одне речення в §5 + тест «429 на 2-й ітерації → `ai_usage` = токени 1-ї».

### В4. `swap_exercise` не перевіряє UNIQUE `(program_day_id, exercise_id)` — `[Так]` падає
- **Де:** §2 (рядок 49): валідація — слот власний, `to_exercise_id ∈ getSubstitutes` і ≠ поточній; доказ обмеження — `src/db/schema.ts:134` `unique("program_exercises_day_exercise").on(programDayId, exerciseId)`; заміни — `src/db/repo.ts:420`.
- **Сценарій:** день «Ноги» містить і «Присідання», і «Жим ногами»; «жим ногами» є серед замін присідання → `propose_change` пройшов валідацію → `[✅ Так]` → оператор (2) batch `UPDATE program_exercises SET exercise_id` порушує UNIQUE → увесь batch (разом з переходом `accepted`) відкочується → користувач бачить «Щось пішло не так» (N9) на кожне натискання, пропозиція лишається `pending` до спливу.
- **Виправлення:** додати до валідації `propose_change` **і** до передумов оператора (1) `NOT EXISTS (SELECT 1 FROM program_exercises WHERE program_day_id = <день слота> AND exercise_id = to_exercise_id)`; збій передумови → `expired` + «Така вправа вже є в цьому дні». До P4.1.4 додати кейс.

### В5. `change_sets_reps` мовчки змінює призначення ваг — це не показано в картці
- **Де:** §2 (рядок 50) і §6 (рядок 93): картка «`«Жим лежачи»: 3 × 6–10 → 4 × 6–8`» не згадує наслідків; інваріант §0 «ваги — лише з рушія».
- **Доказ:** `src/domain/progression.ts:68–69` — `analyze` міряє **минулу** сесію проти **поточного** слота: `success = … reps >= slot.repMax`, `failure = … reps < slot.repMin`.
- **Сценарій:** остання сесія 8/8/8 при діапазоні 6–10 (призначення «повтор +1»). Користувач просить «зроби 6–8», `[Так]` → наступний `prescribeSlot`: `success` (8 ≥ 8) → **`increase` із підвищенням ваги на крок**, хоча жодного нового заняття не було. Навпаки: підняття `rep_min` 6 → 8 при двох минулих сесіях з 7 повторами → `failure` ×2 → `deload` −10 %. Вага змінилась через `[Так]` на «підходи × повтори», у картці про це ні слова.
- **Виправлення:** картка пропозиції містить **порахований кодом** рядок «Наступне призначення: було 60 × 8 → стане 62,5 × 6» (два виклики `prescribeSlot` — з поточним і з новим слотом; чиста функція, без запису). Альтернатива — обмежити `change_sets_reps` лише `sets`; рекомендація — показ, він і чесніший. Додати в §6 і P4.2.4.

### В6. Код-перевірка чисел недільного коментаря не специфікована — відкидатиме майже все
- **Де:** §7 (рядок 103): «кожне число в тексті зустрічається в числах вхідного JSON (інакше коментар відкидається)».
- **Сценарії:** (1) у JSON `volume_kg: 12450` (число), у тексті — «12 450 кг» (неподільний пробіл/пробіл тисяч) → токенізація дає «12» і «450» → відкинуто; (2) `weight_avg: 79.4` у JSON, у тексті «79,4» (десяткова кома, формат `formatKg`) → без нормалізації не збігається; (3) «−0,5 кг» (U+2212) проти `-0.5`; (4) «3 тренування з 4» — `3`, `4` є, але «за 1 тиждень», «2 рази» — малі цілі, яких у JSON нема → відкинуто; (5) модель рахує похідне («+5 %») — відкинуто (це бажано). Без правила 4.3 напише *якийсь* варіант, а ручна перевірка покаже «коментарів майже немає».
- **Виправлення (1 абзац у §7):** число = `\d+(?:[  ]\d{3})*(?:[.,]\d+)?`; нормалізація (прибрати пробіли тисяч, `,`→`.`, `−`→`-`, знак ігнорується); порівняння зі значеннями JSON **у тому форматі, що показує звіт** (округлені так само); дозволений білий список слів-кількостей `1…7` лише поруч зі словами «тиждень/днів/раз/рази/тренувань» **або** просто дозволити цілі 0–10. Тест: «12 450 кг», «79,4», «−0,5» проходять; «+5 %» — ні.

### В7. `chat_turns.text ≤ 2000` проти відповіді до 3 500+ символів — оплачена відповідь губиться
- **Де:** §1 (рядок 27): `text TEXT ≤ 2000`; §5 (рядок 89): вивід «≤ 3500 символів»; §5 (рядок 87): `max_tokens` з текстом → «відправити з приміткою»; `CHAT_MAX_TOKENS = 2000` ≈ 4–6 тис. українських символів.
- **Сценарій:** модель (порада в системному промпті «≤ ~900 символів» не примусова) відповідає на 2 600 символів → конвеєр: (5) `settleAiUsage` виконано → (6) `addChatTurns` порушує CHECK ≤ 2000 → виняток (N9: «Щось пішло не так») → користувач не отримує відповідь, яку вже оплачено, `chat_turns` порожні.
- **Виправлення:** CHECK узгодити (`assistant ≤ 3500`) **і** код обрізає до межі перед записом; порядок (6): спершу відправка користувачу, потім `addChatTurns` (збій запису історії не повинен скасовувати відповідь). Тест на 3 501 символ.

## Дрібниці

- **Д1.** §5 (рядок 79): `costMicro` «бере дорожчу карту, якщо `input_tokens > 100_000`», але розрахунок — «сумою `usage` усіх запитів» (рядок 83). Поріг 100 тис. — за довжиною **промпту одного запиту**, а `src/domain/meal.ts:117` `costMicro(in, out, pIn, pOut)` тарифів не вибирає. Визначити: вартість кожного запиту окремо → сума (на практиці 100 тис. на запит недосяжні: ≈ 18 тис. максимум).
- **Д2.** §6 (рядок 95): передумова `adjust_target` «немає норми з `valid_from = today`» → при порушенні гілка «решта → `expired`, "Програма вже змінилась — попроси ще раз"». Нова людина, у якої `formula`-норму щойно створив перший `/yizha`, або той, хто сьогодні прийняв тренд-пропозицію, просить «знизь норму» → `[Так]` завжди `expired` до завтра, а текст радить «попроси ще раз» (марно; PK `(user_id, valid_from)`). Або `UPSERT` сьогоднішнього рядка (`reason = manual`), або окремий текст «Сьогодні норму вже змінено — спробуй завтра».
- **Д3.** §2 (рядок 40): `get_exercise_history.next_prescription` — «лише якщо вправа є в активній програмі», але вправа може стояти в двох днях з різними `sets`/діапазонами (UNIQUE лише в межах дня). `prescribeSlot(repo, userId, exercise, slot)` (`src/bot/prescribe.ts:6`) потребує конкретного слота: визначити (перший за порядком днів / масив по слотах / вхід `program_exercise_id`). Модуль `src/ai/tools.ts` імпортуватиме з `src/bot/prescribe.ts` — вказати, чи виносити його в `domain`/`ai`.
- **Д4.** §5 (рядок 83): «≤ 6 викликів за хід» — а що, коли одна відповідь містить 7 `tool_use`? Кожен `tool_use` **мусить** мати `tool_result` (інакше наступний запит → 400). Правило: понад ліміт — `tool_result` з `is_error: true` «забагато викликів», а не відкидання.
- **Д5.** §5 (рядок 89) «`esc()`, ≤ 3500 символів»: порядок не заданий. Обрізання **після** `esc` може розрізати сутність (`&am`) → Telegram «can't parse entities»; сам `esc` розтягує `&` до 5×. Визначити: обрізати сирий текст ≤ 3500 → `esc` → якщо > 4096 − (довжина статичного рядка й примітки), обрізати ще; тест на межі (N6).
- **Д6.** §7: `buildReport` викликається **після** заявки — `src/reminders.ts:166` (`claimReminder`) → `:172` `buildReport`. Додавання 10-секундного виклику ШІ всередині подовжує вікно «заявлено, ще не надіслано» (крах Worker у ці 10 с = пропущений звіт, `phase-2.md` §«заявити → надіслати»). Або викликати ШІ **до** заявки (після `wanted`), або принаймні записати як прийняту ціну; `buildReport` зараз не отримує ні ключа, ні `fetch` — 4.3 розширить `PairCtx`.
- **Д7.** §1: `createProposal` рахує ліміт і UNIQUE за `status = 'pending'`, а прострочені (`expires_at ≤ now`) лишаються `pending`, доки не пройде крон. Після пропуску тіка пропозиція, недосяжна кнопкою (ледаче прострочення), ще блокує створення нової. `createProposal` має ігнорувати/гасити `pending` з `expires_at ≤ now`.
- **Д8.** §1 (рядок 27) `DELETE … id NOT IN (SELECT id … ORDER BY id DESC LIMIT 10)` — «…» приховує `user_id` у підзапиті й у `DELETE`; без нього тест із двома користувачами стирає чужі рядки (N8). Додати в P4.1.7 другого користувача; уточнити: «10 рядків» = 5 пар (два `INSERT` пари одним batch гарантують парність).
