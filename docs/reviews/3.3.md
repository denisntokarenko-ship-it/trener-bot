# Рев'ю 3.3 — Розпізнавання їжі за фото (PR #38)

Рев'юер: незалежна сесія (не автор). Гілка `phase-3/03-food-photo`, коміт `4df2e41`. Код не змінювався; єдиний створений файл — цей.

## Вердикт: ПРИЙНЯТИ ПІСЛЯ ВИПРАВЛЕНЬ

Блокерів немає. Усі твердження автора підтвердилися, п'ять пунктів, на які просив глянути оркестратор, — виконано (деталі нижче). Але мої мутанти знайшли **захисти, що є в коді й не охоплені жодним тестом**, серед них два про гроші й безпеку (В1, В2), а також одну дрібну логічну помилку (В4). Усе виправляється малими тестами й однією невеликою правкою.

Живий прохід із ключем (5 фото, `between_tools` разом з `output_config.format`, `cpuTime`) **не перевірено** — за домовленістю це не блокер.

## Блокери

## Важливе

**В1. Захист «збій до відправки → зняти резервування» не має тесту.** `src/bot/meal-flow.ts:192–195`. Мутант: прибрати `if (!sent) await release();` у гілці `if (!f)` → 101/101 тестів зелені. Будь-який виняток між резервуванням і відправкою (D1 у `knownFoodNames`, `new Anthropic`, `arrayBuffer` без дедлайну) інакше лишає 15 000 мкUSD «спалених» без виклику; 20 таких збоїв за день = 300 000 = ліміт вичерпано без жодного платного запиту. Тест: інʼєктувати збій у `knownFoodNames` (або зламаний ключ/конструктор) → `ai_usage` порожня, клієнт не викликано.

**В2. Екранування назви продукту від моделі не має тесту.** `src/bot/texts.ts:882` (`esc(l.nameUk)`; те саме в `mealGramsPrompt`). Мутант без `esc` → 101/101 зелені. Назва приходить із фото (текст на фото → модель → `name_uk`), проходить `parseItem` (1–60 символів, Атуотер від назви не залежить). Без `esc`: `<a href="http://evil">…` стає клікабельним посиланням у повідомленні бота, а `<` без закриття — «can't parse entities» (прийом `pending` є, повідомлення з кнопками — ні). Тест: відповідь із `name_uk` = `<b>x</b> & y` → у `sendMessage` текст містить `&lt;b&gt;`.

**В3. Обрізання підпису до 300 символів і верхня межа розміру файлу без тестів.** (а) `meal-flow.ts:252` — мутант `msg.caption` без `slice` виживає; підпис 1000 символів (Telegram дозволяє до 1024) інакше йде в запит повністю й падає на `CHECK caption <= 300` у `createPendingMeal` — **платний виклик відбувся, а прийому немає**. (б) `meal-flow.ts:152` — мутант без `bytes.length > FOOD_PHOTO_MAX_BYTES` виживає: `file_size` у `PhotoSize` необов'язковий, `pickPhoto` бере кандидата без розміру, 8 МБ-JPEG пройде перевірку `FF D8 FF` і піде в Anthropic (≈11 МБ base64). Два тести: підпис 1000 → у запиті ≤ 300, прийом створено; завантаження 3 МБ → «Не вдалося прочитати фото», резервування знято, клієнт не викликано.

**В4. Невдалий `createPendingMeal` лишає `ai_estimate` еталоном на добу.** `meal-flow.ts:215–227`. Продукти створюються до прийому; якщо `createPendingMeal` кидає виняток (CHECK, збій D1) або повертає `null`, нові `ai_estimate` лишаються: крон чистить сиріт із порогом 24 год (`expirePendingMeals`). Сценарій: «борщ» оцінено → прийом не створено → через хвилину те саме фото знаходить аліас «борщ» і бере відкинуту оцінку як еталон. Спека §1 «відкинута оцінка не стає еталоном» порушена на добу. Виправлення: у `catch`/`null`-гілці прибрати щойно створені (їх id відомі з циклу) осиротілі `ai_estimate` — функція чистки вже є (`orphanEstimates` усередині `cancelMeal`/`updateMealGrams`), потрібен експорт у repo або виклик `cancelMeal`-подібного шляху; плюс тест.

## Дрібниці

## Окремі питання оркестратора

1. **Ліміт витрат.** `reserveAiUsage` — один умовний `INSERT … SELECT` (3.1, перевірено в рев'ю 3.1); у потоці резервування — до створення клієнта; 10 паралельних фото при залишку на 2 → 2 виклики (тест + мутанти M1/M1b вбиті). Release: HTTP-помилка з кодом → `release` (429/5xx/4xx — тести), дедлайн до відправки → `release`, після відправки → оцінка лишається. Дірка лише одна — В1 (нема тесту, код правильний).
2. **Токен/URL Telegram.** Адреса файлу з токеном будується лише в `download()` для `fetch` усередині Worker; до Anthropic йдуть base64-байти; логи містять лише `errorName`/`status`. Тест звіряє тіло, заголовки, URL запиту й усі `console.*` на `api.telegram.org`, токен і ключ. Витоку не знайдено.
3. **ШІ не пише без кнопки.** `createPendingMeal` створює лише `pending`; єдиний шлях до `confirmed` — `confirmMeal` у callback `m:y` власника; мутант M3 (автопідтвердження) вбито.
4. **Інʼєкція через підпис.** Підпис — у `<user_caption>`, `<`/`>` замінено на `‹›` (тест із `</user_caption>`), system-промпт трактує підпис і текст на фото як дані, вихід обмежений JSON-схемою, `parseFoodResponse` (межі, Атуотер, ≤ 8), далі `esc()` і людина з кнопкою. Лишилися лише прогалини в тестах (В2, В3а, Д3).
5. **Відхилення автора.** (а) `waitUntil` через `telegramHandler` — прийнятно: `handleRequest` не змінено, без `waitUntil` (тести) обробник чекає фонову роботу. (б) ASCII-скрипт ключа — я прочитав: `Read-Host -AsSecureString`, перевірка формату без виводу ключа, значення йде в `wrangler secret put` через stdin (той самий спосіб, що в `setup-secrets.ps1`, яким уже заведено живі секрети), змінні чистяться у `finally`. (в) SDK шле `Authorization: Bearer` — підтверджено кодом SDK (`client.js`, `apiKeyAuth`); додатково я зробив один пробний запит із **фіктивним** ключем: сервер відповів `401 invalid x-api-key` (отже заголовок читається як ключ), SDK у workerd працює з дефолтним `fetch`, а `classifyAiError` дає `unavailable` + `refund`. Чи приймає API справжній ключ у такому вигляді — **не перевірено** (немає ключа).
