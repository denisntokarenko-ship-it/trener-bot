# Фаза 2 — Метрики й нагадування

## Стан

**Оновлено:** 2026-11-20 · **Зріз:** специфікація Фази 2 (завдання 2.0) · **Читають:** 2.1–2.5 разом із `00-common.md`.
**Спирається на 1b:** анкета вже зібрала вагу (`user_profiles.weight_kg`), `days_per_week`, назви днів («Все тіло A (ноги, груди, спина)») — Фаза 2 їх **не збирає вдруге**. Припущення — у «Невідоме» (**[П]**). Блокуючих питань немає.

## Задача

Бот сам нагадує про тренування й зважування, веде вагу тіла, показує повний прогрес і щонеділі надсилає звіт. Усі цифри рахує код; текст шаблонний (ШІ-коментар додасть Фаза 4).

## 1. Модель даних

Дві міграції (по одній у завданні, що нею користується; номери — наступні за наявними, на старті 2.1 `0004`). `reminders_sent` створює **лише 2.3** — 2.1 від неї не залежить.

**2.1 — `body_weights`**: `user_id` → `users.id`, `local_date` TEXT `YYYY-MM-DD` (локальна дата за `users.tz` на момент запису), `weight_dg` INTEGER CHECK 300–3000 — вага в **десятих кілограма** (78,4 кг = 784), щоб середні й різниці були цілочисельними й детермінованими; `updated_at` UTC мс. PK (`user_id`, `local_date`): запис за день **перезаписує** (upsert). Заднім числом не пишемо — дата завжди «сьогодні за `users.tz`».

**2.3 — `users` + `reminders_sent`** (`ALTER TABLE ADD COLUMN`; CHECK — лише в SQL, як у 1b.1, `schema.ts` їх не бачить):
- `training_days` TEXT NOT NULL DEFAULT `'1,3,5'` — ISO-дні 1 (Пн)…7 (Нд), через кому, зростаюче, без повторів, ≥ 1 день. CHECK у SQL слабкий (`GLOB '[1-7,]*'`, непорожній); порядок, унікальність і ≥ 1 день перевіряє домен/repo (тест на `2,1`, `1,1`, порожнє, `8`).
- `remind_time` TEXT NULL DEFAULT `'08:00'` — `HH:MM`, кратне 15 хв, 05:00–22:00; `NULL` = вимкнено. CHECK: `remind_time IS NULL OR (remind_time GLOB '[0-2][0-9]:[0-5][0-9]' AND substr(remind_time,4) IN ('00','15','30','45') AND remind_time BETWEEN '05:00' AND '22:00')`.
- `weigh_time` TEXT NULL DEFAULT `'07:30'` — те саме; `NULL` = вимкнено.
- Бекфіл у міграції: `training_days` за `user_profiles.days_per_week` через `CASE` — 2 → `1,4`; 3 → `1,3,5`; 4 → `1,2,4,5`; 5 → `1,2,3,4,5`; **`ELSE '1,3,5'`** (профіль створюється вже на `/start`, `days_per_week` може бути `NULL`).
- `reminders_sent`: `user_id`, `kind` IN (`train`,`weigh`,`report`), `local_date` TEXT, `sent_at` UTC мс, `message_id` INTEGER NULL. PK (`user_id`,`kind`,`local_date`). Не чиститься (≈ 3 рядки/день; TTL не потрібен).
- `cron_state` (`id` INTEGER PK CHECK `id = 1`, `last_tick_at` UTC мс, `last_ok_at` UTC мс NULL — міграція `0006`): `last_tick_at` оновлюється наприкінці **кожного** тіку (навіть якщо нагадування кидали), `last_ok_at` — лише коли тік пройшов без помилок (`errors = 0`: ні збою прибирання, ні нагадувань, ні невизначеної долі відправки). `/health` лишається `200`, тіло починається з `ok` і додає ` cron=7m ok=7m` (вік тіку й вік тіку без помилок у хвилинах; `?` — такого тіку ще не було). Тік, що впав, «живим» не виглядає: `ok` старішає. 2.5 перевіряє `ok < 20m`.

Доступ лише через `src/db/repo.ts` з `userId` (N8). Вага з анкети **не копіюється** в `body_weights` (знімок без дати; міграція не вгадує локальну дату).

## 2. Вага тіла

### Введення

`/vaga 78.4` (або `78,4`) → запис за сьогодні. Формат `^\d{2,3}([.,]\d{1,2})?$`. Рядок парситься в цілі соті, **половина округлюється вгору** до десятих (78,45 → 78,5; 29,96 → 30,0), і лише **після округлення** перевіряється діапазон 30,0–300,0; зберігається `weight_dg`. Жодних `float`-округлень у коді.
- Відповідь: `⚖️ 78,4 кг записано (середнє за 7 днів: 78,9 кг)`; перезапис — `… записано, замінило 78,6`.
- Стрибок > 5 кг до попереднього запису (≤ 14 днів тому) — приймається, у відповідь рядок `Різниця +6,2 кг — якщо помилка, надішли ще раз: /vaga 78.4`. Підтвердження-кнопки немає (не додає стану); перезапис дня виправляє.
- `/vaga` без числа → остання вага з датою, середнє, `Записати: /vaga 78.4`.
- Невалідне → `Не схоже на вагу. Приклад: /vaga 78.4`.

### Як відрізнити число від ваги в тренуванні (кроки 1 і 4 додає 2.3, коли зʼявляється `reminders_sent`)

Текст від власника перевіряється **у цьому порядку, перший збіг виграє** (зміна в `bot.ts`, гілка `message:text`):
1. *(2.3)* **Відповідь (reply) на нагадування про зважування:** `reply_to_message.message_id` = `reminders_sent.message_id` для `kind = weigh` **і** `reminders_sent.local_date` = сьогодні → вага тіла. Явний жест виграє навіть над очікуванням ваги вправи. Якщо `local_date` старіша: нічого не пишемо, відповідь `Це нагадування за вчора. Надішли /vaga 78.4 — запишу на сьогодні`.
2. `workouts.await_input ≠ NULL` (вага вправи, Фаза 1) → як у `phase-1-flow.md`.
3. Активна анкета (`onboarding_state.status = active`) → як у 1b.
4. *(2.3)* **Голе число** (той самий формат, що `/vaga`, без команди) і є рядок `reminders_sent (weigh, сьогодні)` без `body_weights` за сьогодні → вага тіла. Нагадування «відкрите» до кінця локальної доби або до зважування.
5. Інакше голе число → стандартна відповідь «не зрозумів» Фази 1 (`NOT_UNDERSTOOD` у `texts.ts`; рядок + підказка) + для чисел 30–300: `Вагу тіла записують так: /vaga 78.4`. Голе число без відкритого нагадування **ніколи** не пишеться в `body_weights`. У 2.1 (без кроків 1 і 4) діють кроки 2, 3 і 5.

Чому так: число 45 у залі без очікування ваги раніше було «Не розумію», тож крок 4 нічого не ламає; пастка — лише число між підходами при відкритому ранковому нагадуванні, і відповідь завжди показує, що записано, а `/vaga` виправляє за один крок.

### Середнє й зміна

Усе — за **локальними датами**, не за 168 годин (у дні переходу час доби має 23/25 год).
- **Вікна:** `W0` = 7 локальних дат, що закінчуються сьогодні (`сьогодні−6 … сьогодні`); `W1` = попередні 7; `W2` = ще попередні 7. Скрізь на екранах ваги «тиждень» означає ці ковзні вікна (лише звіт — календарні Пн–Нд).
- **Середнє 7 днів** = сума десятих / n, ділення з округленням половини вгору до десятих. 0 записів → `—`; 1–2 → з приміткою `(n зваж.)`; ≥ 3 — без.
- **Зміна до минулого тижня** = `avg(W0) − avg(W1)` на неокруглених середніх: `(S0·n1 − S1·n0)/(n0·n1)` десятих, лише якщо в **обох** вікнах ≥ 2 записів, інакше `—`. Показ: округлення половини **від нуля** до десятих; якщо результат 0 (напр. −0,04) — `0,0` без знаку; інакше `−` (U+2212) або `+`; десяткова кома.
- **Старт** для тренду: вага з анкети (`user_profiles.weight_kg`) з підписом `з анкети`; немає — перший запис `body_weights`. **Зараз** = середнє `W0`, а без записів у `W0` — останній запис з датою.

## 3. Повний `/progres`

`/progres` показує екран: вага тіла + вправи; кнопка [📜 Останні тренування] редагує повідомлення на старий список із Фази 1 (`phase-1-flow.md`, P2.5), [⬅️ Назад] повертає. Дані екрана — три запити (вага, агрегат за вправами, останні тренування), не цикл по вправах.

```
📈 Прогрес
⚖️ Вага: 82,0 (анкета) → 79,4 (середнє 7 днів) · −2,6 кг
   Тиждень до тижня: −0,4 кг · 7-денні вікна: 80,1 · 79,8 · 79,4
Присідання зі штангою
   Старт 40 × 8 → зараз 60 × 8 · рекорд 62,5 × 6 (23.10)
   e1RM ≈ 76 кг
Тяга верхнього блока
   …
```

**Визначення** (чисті функції без I/O, час параметром):
- **Сесія вправи** — як у `00-common.md`; рахуються лише непропущені підходи з вагою й повторами.
- **Старт** = «найкращий підхід» першої сесії, **Зараз** = «найкращий підхід» останньої. Найкращий підхід сесії — максимум e1RM серед її підходів із повторами ≤ 10; немає таких → найбільша вага.
- **e1RM (Еплі)** = `w × (1 + r/30)`, `r = 1` → `w`. **Межа повторів 10:** підходи з `r > 10` у e1RM не беруться (формула стає ненадійною). Відображення — до 0,5 кг. Для ваги тіла (`weight_step_kg = 0`) e1RM немає, лише повтори. Якщо жоден підхід вправи не має `r ≤ 10`, рядок e1RM пропускається.
- **Рекорд** = як у підсумку тренування Фази 1: найбільша вага непропущеного підходу з ≥ 1 повтором, з максимумом повторів на ній, з локальною датою рекорду; для ваги тіла — максимум повторів. **Без вікна:** агрегат по всій історії (виправляє борг F-1 Д2 — вікно 30 сесій); підсумок тренування й `/progres` користуються тим самим запитом.
- **Рекордом першої сесії** вправи рекорд не вважається в *підсумку* (калібрування); у `/progres` вона просто дає «Старт = Зараз».
- **Тренд ваги тіла:** середні `W2 · W1 · W0` (від старого до нового; вікно без записів пропускається) — ті самі вікна, що й «Тиждень до тижня», тож цифри на екрані сходяться.
- Вправи — лише ті, що мають ≥ 1 зарахований підхід; порядок — за датою останньої сесії, нові зверху. Назви — як у Фазі 1. Текст > 4096 → відкидаються вправи з найстарішою останньою сесією (N6). Немає ні ваги, ні тренувань → `Ще немає даних. Почни: /trening, вага: /vaga 78.4`.

## 4. Нагадування й крон

Тригер один — `*/15 * * * *` (з двома середовищами — preview і production — два тригери на акаунт; ліміт платного тарифу не загрожує, **2.5 перевіряє** ліміти тригерів і wall-time запланованого обробника). `runCron` — **два незалежні `try/catch`**: прибирання Фази 1 і нагадування; збій одного не зупиняє другого. Усередині нагадувань — окремий `try/catch` на кожну пару (користувач, `kind`): некоректний `tz` (RangeError від `Intl`) чи виняток repo в одного не блокує інших. Пари виконуються паралельно (`Promise.allSettled`). Наприкінці тіку — `cron_state` і один `console.log` з лічильниками `{sent, skipped, released, errors}` (без текстів).

### Коли нагадування «має піти»

Для користувача з `tz`: `L` = локальна дата й час тіку (через `Intl`, **ніколи** не «T у UTC»). Нагадування `kind` з часом `T` належить до тіку, якщо одночасно:
1. локальна дата `L` — та сама, що й дата запису в `reminders_sent`; день тижня `L` ∈ `training_days` (для `train`);
2. `0 ≤ minutes(L) − T < 60` для `train` і `weigh` (тіки кратні 15 хв, останній тік вікна — `T+45`; пропущений тік не губить нагадування, а пізніше ніж на годину — теж пропуск; вікно не переходить північ, тож `T ≤ 22:00`). Для `report` вікно — до кінця локальної доби (пізній звіт кращий за жоден);
3. немає рядка `reminders_sent (user, kind, local_date)`.

Чому 60, а не 15 хв: один-два пропущені тіки (збій Cloudflare, помилка Telegram) не мають губити нагадування. Діапазон `05:00–22:00` не зачіпає годин переходу Europe/Kyiv (03:00–04:00); ключ `local_date` додатково захищає від дубля в поясах, де перехід припадає на інший час.

### Порядок «записати → надіслати»

Обрано **«заявити → надіслати → при помилці зняти заявку»**:
1. `INSERT INTO reminders_sent … ON CONFLICT DO NOTHING`; вставлено 0 рядків → нічого не робити (інший тік уже взяв).
2. `sendMessage`; успіх → `UPDATE … SET message_id`.
3. **Визначена недоставка** (відповідь Telegram зі статусом ≥ 400, у т.ч. 403/429; помилка до відправки) → `DELETE` заявки, лог без тексту й секретів (N9); наступний тік у межах вікна повторить. **Неоднозначна** (таймаут 5 с через `AbortController`, обрив мережі): Telegram міг прийняти запит — заявку **лишаємо** (`message_id` NULL), лог `warn`; повтору не буде — пропущене краще за подвійне.

Чому не «надіслати → записати»: збій між ними дає **подвійне** нагадування — дратує й ламає N3. Недолік обраного — крах Worker'а *між* кроками 1 і 2 губить нагадування (немає ні рядка-свідка, ні повідомлення): прийнято, пропущене нагадування дешевше за подвійне, а сам збій на Cloudflare — рідкість. `message_id` NULL у заявки з крахом лишається; крок 4 розділу 2 тоді не працює (відповідь-reply не збігається) — лишається `/vaga`.
- **429** (`retry_after`) — як будь-яка помилка: зняти заявку, наступний тік (≥ 15 хв) — у межах вікна. **403** (бота заблоковано) — те саме; повторюється кожен тік у вікні, потім день пропущено (один користувач — ліміт не загрожує).
- Пари (користувач, `kind`) обробляються паралельно; помилка однієї не блокує інших.

### Нагадування про тренування (`train`)

Умови: день тижня ∈ `training_days`, `remind_time` ≠ NULL, є активна програма, **немає** тренування сьогодні (за локальною датою `started_at`; `active` теж рахується). Текст (день — `dayName`, призначення — `nextPrescription`, що й `/prohrama`):

```
🏋️ Сьогодні тренування — Все тіло A (ноги, груди, спина)
Присідання зі штангою — 60 кг × 8
Жим лежачи — 45 кг × 8
…
Почати: /trening
```
- Наступний день — `nextDayCode(останнє done, дні програми)`; **вимога:** `nextDayCode` рахує від останнього `done` **активної** програми, після активації нового плану дає перший день за `position` (тест P2.3.12; правка 1b-коду входить у 2.3).
- Слот без історії → `калібрування, старт ≈ N кг` (як у `/prohrama`); текст ≤ 4096 (N6), довгий список різати з кінця.
- Пропущене тренування не карається: наступне нагадування покаже той самий день.

### Нагадування про зважування (`weigh`)

Щодня о `weigh_time`, якщо `weigh_time ≠ NULL` і `body_weights` за сьогодні немає: `⚖️ Доброго ранку! Вага? Надішли число у відповідь (наприклад 78.4) або /vaga 78.4`. Відкриває вікно кроку 4 розділу 2.

### Недільний звіт (`report`)

Нд о **19:00** локального часу (константа в `src/config.ts`, у налаштуваннях не змінюється). Без тренувань і ваги за весь час — мовчки пропускається. Тиждень — **7 локальних дат Пн–Нд**, межі в UTC обчислюються `localDayStartUtc(date, tz)` (локальна північ; у дні переходу доба 23/25 год).

```
📊 Тиждень 19–25 жовтня
Тренувань: 3 з 3 · Підходів: 41 · Обсяг: 18 240 кг
🏆 Нові рекорди: Присідання зі штангою — 62,5 кг × 6
⚖️ Середня вага 79,4 кг (−0,4 до минулого тижня)
Далі: Все тіло B (…) — /trening
```
- «з N» = кількість `training_days`. Обсяг — як у підсумку Фази 1. «Тренувань» = `done`, чия локальна дата `started_at` у Пн–Нд тижня (розпочате Нд 23:50 — у цьому тижні). Нових рекордів ≤ 3: рекорд тижня = нова макс. вага вправи (перша сесія не рахується), відбір — за приростом ваги над попереднім рекордом спадно, при рівності — за назвою; немає — рядка немає. Діапазон: `19–25 жовтня`, через місяць — `28 жовтня – 3 листопада` (родовий відмінок). Ваги тіла немає — рядка немає.
- 0 тренувань: `Цього тижня тренувань не було. Нічого страшного — далі: … /trening`, без докорів.
- Звіт формує `buildWeeklyReport(...)` → структура, потім рендер; Фаза 4 додає текстове поле коментаря в ту саму структуру.

### Переходи часу (Europe/Kyiv)

**2026-10-25, Нд, EEST → EET** о 04:00 → 03:00 (UTC 01:00; локальна доба 25 год; `2026-10-24T21:00Z … 2026-10-25T22:00Z`). `localDayStartUtc(date, tz)` — зсув `tz` на `00:00` через `Intl` двома ітераціями (`t = UTC-північ − offset(t)`); якщо локальної опівночі немає — перший наявний момент після неї.
- `weigh_time = 07:30`: у Сб 07:30 EEST = 04:30Z, у Нд 07:30 EET = 05:30Z — час задається локально, а не зсувом у UTC; заявка `(weigh, 2026-10-25)` одна, повторний тік 05:45Z нічого не шле.
- `remind_time = 08:00` у цю Нд — 06:00Z (у Сб було 05:00Z); тік 06:00Z, що випав, покривають 06:15Z–06:45Z.
- Звіт 19:00: тиждень Пн 19.10 — Нд 25.10 = 7 дат, але 169 год; вікна ваги/тренувань рахуються за датами, тож жоден запис не губиться й не потрапляє двічі.

**2027-03-28, Нд, EET → EEST** о 03:00 → 04:00 (UTC 01:00; доба 23 год; `2027-03-27T22:00Z … 2027-03-28T21:00Z`).
- `weigh_time = 07:30` — 04:30Z у Нд (у Сб 05:30Z); тік 04:30Z, що випав, компенсують тіки 04:45Z–05:15Z (≤ `T+45`); тік 05:30Z (= `T+60`) уже не шле.
- `remind_time = 08:00` — 05:00 UTC (раніше 06:00 UTC); вікно звичайне.

Тести (2.3) із фіксованим `now` покривають обидва приклади і обидві межі вікна (`T−1`, `T`, `T+45`, `T+60`); `reminders_sent` лишається ключем ідемпотентності.

### Інше

- Два нагадування в один тік (напр. 07:30 вага й 08:00 тренування при тіку 08:00) — окремі повідомлення.
- Зміна `tz` посеред дня може дати 0 або 2 нагадування за цей день (ключ `local_date` у новому поясі) — прийнято, **[П]**.
- CPU: тік читає користувачів і до трьох нагадувань; N1 на проді вже > 5 мс (`PROGRESS.md`, борг [0.4]) — у 2.5 заміряти тік `*/15` у `wrangler tail`, ціль — `outcome: ok` без `exceededCpu`.

## 5. `/nalashtuvannia`

Один екран, редагується на місці (`msg_id` у `callback_data` не потрібен: `editMessageText` викликається на повідомленні кнопки). Стану в БД **немає** — усе кнопками, крім часового поясу (командою з аргументом).

```
⚙️ Налаштування
📅 Дні тренувань: Пн, Ср, Пт
🏋️ Нагадування про тренування: 08:00
⚖️ Нагадування про вагу: 07:30
🌍 Часовий пояс: Europe/Kyiv
[📅 Дні] [🏋️ Час] [⚖️ Час] [🌍 Пояс] [👤 Профіль]
```
- **Дні:** семикнопковий перемикач Пн…Нд (✅ на обраних) + [Готово]; мінімум 1 день (останній не знімається — тост «Потрібен хоча б один день»).
- **Час:** сітка годин 05–22, потім `:00 :15 :30 :45`; [🔕 Вимкнути] ставить `NULL`. Кроки кратні 15 хв — відповідають тіку.
- **Пояс:** кнопка показує `Надішли: /nalashtuvannia Europe/Warsaw`. Команда з аргументом валідує: `^[A-Za-z]+(/[A-Za-z0-9_+-]+){1,2}$`, ≤ 40 символів, префікс `Etc/` відхиляється, далі `new Intl.DateTimeFormat("en",{timeZone})` без винятку; зберігається те, що повернув `resolvedOptions().timeZone` (канонічно за ICU рантайму; тест звіряє з рантаймом, а не з літералом). Невалідне → `Не знаю такого поясу. Приклад: Europe/Kyiv, Europe/Warsaw`.
- **Профіль** — кнопка веде в `/profil` (1b): стать, рік, зріст, вага, ціль, рівень, дні/тривалість, обмеження **не дублюються** тут.
- Кількість обраних днів ≠ `days_per_week` профілю → під екраном `План розрахований на 3 дні, обрано 4 — це лише нагадування`. Активація нового плану (1b) з іншим `days_per_week` скидає `training_days` до дефолту для нового N і повідомляє про це одним рядком.
- Callback-и — префікс `s:`, застарілі/зайві → як у Фазі 1 (`answerCallbackQuery`, без запису). Кожна кнопка йде через перевірку власника (N8); значення часу й днів у `callback_data` перевіряються на сервері, не довіряються.

## 7. Історії

Кожна — окремо тестована; час у тестах фіксований (`setSystemTime`/параметр).

**P2.1 — Вага тіла (2.1).**
1. **Given** немає запису, **When** `/vaga 78,4`, **Then** рядок за локальну дату; **When** `/vaga 78.0` того ж дня, **Then** той самий рядок, значення замінено, відповідь `замінило 78,4`.
2. **Given** 23:30 за Києвом (UTC уже наступна доба), **When** `/vaga`, **Then** локальна дата, не UTC.
3. **Given** `/vaga 29` · `301` · `abc` · `78.456` · `78,`, **Then** жодного запису, підказка формату.
4. **Given** записи за 7 днів 79,0 · 78,8 · 78,6 і минулий тиждень 79,4 · 79,2, **When** середнє, **Then** 78,8; зміна **−0,5** (78,8 − 79,3); **Given** у `W1` один запис, **Then** зміна `—`; один запис у `W0` → `(1 зваж.)`; **Given** `78,45` → 78,5; `29,96` → 30,0 (приймається); `29,94` → відмова; зміна −0,04 → `0,0`.
5. **Given** `await_input ≠ NULL` і число, **Then** це вага вправи (не `body_weights`). *(Кроки з reply і відкритим нагадуванням — P2.3.10.)*

**P2.2 — `/progres` (2.2).**
1. **Given** сесії присідань 40×8 (перша) і 60×8, 62,5×6 (рекорд 23.10), **When** `/progres`, **Then** `Старт 40 × 8 → зараз 60 × 8 · рекорд 62,5 × 6 (23.10)` і e1RM за Еплі: 60×8 → 76,0, 62,5×6 → 75,0; «зараз» — найкращий підхід останньої сесії.
2. **Given** підхід 20 × 15, **Then** у e1RM не бере участь; вправа лише з такими підходами — без рядка e1RM, рекорд за вагою.
3. **Given** 40 сесій вправи, **Then** рекорд не залежить від вікна (мутант: вікно 30 → тест червоний); підхід r = 1 → e1RM = вага.
4. **Given** вправа лише з пропущених підходів, **Then** її в списку немає. Вага тіла без записів → рядок ваги з анкети або відсутній.
5. **Given** текст > 4096, **Then** найстаріші вправи відкинуто. [📜 Останні тренування] ↔ [⬅️ Назад] редагують те саме повідомлення; чужий користувач — тиша (Фаза 0).

**P2.3 — Нагадування (2.3).**
1. **Given** `training_days = 1,3,5`, Пн 08:00 за Києвом, **When** тік, **Then** одне повідомлення з назвою дня й призначеннями; **When** другий тік тієї ж години, **Then** нічого (рядок у `reminders_sent`).
2. **Given** тренування вже було сьогодні (done/active) або Вт, **Then** `train` не надсилається, і заявки немає.
3. **Given** `sendMessage` кидає, **Then** заявку знято, наступний тік у вікні надсилає; **When** помилка триває вікно, **Then** день пропущено, `reminders_sent` порожній.
4. **Given** тіки `T−1`, `T`, `T+45`, `T+60` хв, **Then** `T−1` і `T+60` нічого не шлють, `T` шле, `T+45` після `T` — ні (заявка); без `T` — `T+45` шле. `report` о 20:30 — шле (вікно до кінця доби).
5. Дні переходу з розділу 4 — два сценарії зі `now` у UTC.
6. **Given** `remind_time = NULL`, **Then** `train` немає; **Given** вага вже є, **Then** `weigh` немає.
7. **Given** Нд 19:00 і тиждень зі звітом із розділу 4, **Then** текст збігається зі знімком; нуль тренувань — варіант без докорів; нічого немає → мовчить; крон прибирання працює, навіть якщо нагадування кидають, і навпаки (`purge…` кидає — нагадування йдуть).
8. **Given** гонка (два паралельні тіки), **Then** рівно одне повідомлення (UNIQUE). **Given** `tz = "Bad/Zone"` в одного користувача, **Then** інший отримує нагадування.
9. **Given** `sendMessage` повертає 429/403, **Then** заявку знято; **Given** таймаут/обрив, **Then** заявку **лишено**, повтору немає (мутант «зняти на таймаут» — червоний).
10. **Given** reply на нагадування за сьогодні, **Then** вага тіла, `await_input` не чіпається; reply на вчорашнє — відмова з підказкою, запису немає; голе число при відкритому нагадуванні — вага тіла; без нього — `Не розумію` + підказка, запису немає; після зважування голе число — підказка.
11. **Given** кожен тік, **Then** `cron_state.last_tick_at = now`, `/health` показує вік тіку й тіку без помилок (тік без токена: `cron` свіжий, `ok` старіє); `localDayStartUtc`: 2026-10-25 = `2026-10-24T21:00Z`, 2026-10-26 = `2026-10-25T22:00Z`, 2027-03-28 = `2027-03-27T22:00Z`, 2027-03-29 = `2027-03-28T21:00Z`.

## Поза межами

Ввід ваги заднім числом, графіки й картинки, експорт історії, окремий час звіту, ескалація нагадувань («пауза після N ігнорувань»), ШІ-коментар (Фаза 4), корекція норми за вагою (Фаза 3), зміна даних профілю в `/nalashtuvannia`.

## Невідоме

- **[П] `/nalashtuvannia` без даних профілю** — вони в `/profil` (1b), тут лише розклад і пояс; кнопка-перехід замість дубля.
- **[П] Вага з анкети — «Старт»**, не рядок `body_weights`; Фаза 3 бере норму з останнього запису `body_weights`, а немає — з анкети.
- **[П] Дні нагадувань ≠ `days_per_week`** допустимі (лише нагадування); розбіжність показується, план не перебудовується. Новий план скидає дні.
- **[П] Звіт у Нд 19:00**, не налаштовується. **[П] Вікно 60 хв**, `T ≤ 22:00`.
- **[П] Пояс командою з аргументом** (не станом): менше коду й жодного нового стану поруч з `await_input`. Зміна `tz` посеред дня може дати 0/2 нагадування того дня.
- **[П] Голе число при відкритому нагадуванні** вважається вагою тіла (крок 4): ризик — число між підходами; пом'якшує відповідь із явним записом і перезапис `/vaga`.
- **[П] «Старт» ваги = `user_profiles.weight_kg`:** якщо змінити вагу в `/profil`, «Старт» змінюється разом із нею; `/profil` не оновлюється від `/vaga`. Прийнято (Фаза 3 бере останній `body_weights`).
- **[П] Тиха відмова крону:** `cron_state` + `/health` і лічильники в лозі; зовнішній «мертвий вимикач» (сповіщення) — поза Фазою 2.
- **[П] `Intl.DateTimeFormat`** у Workers підтримує IANA; результат (`Europe/Kyiv` чи `Europe/Kiev`) залежить від ICU рантайму — зберігається як повернув рантайм.
- **[ПОТРІБНО УТОЧНИТИ: чи потрібне нагадування про вагу щодня]** — припущення: щодня; пропустити можна, ескалації немає.
- Блокуючих питань немає.
