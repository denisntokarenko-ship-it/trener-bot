## Задача

## 1. Потік фото (3.3)

**Вхід.** `message:photo` від власника (білий список — Фаза 0). Файл-картинка (`document` з `image/*`) → «Надішли фото не файлом — так я його розпізнаю». Альбом: кожне фото — окремий прийом і виклик (обмежує ліміт).

**Крок 0 — до коштів.** Немає `ANTHROPIC_API_KEY` → «Розпізнавання ще не підключене» (лог без значення). **Резервування ліміту** — один атомарний `reserveAiUsage`: `INSERT INTO ai_usage (…, cost_micro = FOOD_CALL_EST_MICRO, input_tokens = 0, output_tokens = 0, local_date) SELECT … WHERE (SELECT COALESCE(SUM(cost_micro),0) FROM ai_usage WHERE user_id = ? AND local_date = ?) + FOOD_CALL_EST_MICRO ≤ AI_DAILY_LIMIT_MICRO`; 0 змін → «Денний ліміт розпізнавання вичерпано. Спробуй завтра», **клієнт Anthropic не викликається**. Один оператор D1 серіалізує паралельні фото: альбом з 10 фото не обходить ліміт (кожне бачить резервування попередніх). Рядок резервування і є облік: після відповіді `settleAiUsage` замінює оцінку фактичною ціною з `usage`; HTTP-помилка API (4xx/5xx — не оплачується) або дедлайн **до відправки** запиту в Anthropic → `releaseAiUsage` (DELETE); обрив/таймаут **після** відправки → рядок лишається з оцінкою (запит міг бути оплачений); Worker, убитий будь-де після резервування, лишає оцінку, а не нуль.

**Робота — у `ctx.waitUntil`** (N2): вебхук одразу 200, `telegramHandler` отримує `ctx` (змінюється сигнатура `UpdateHandler` у `src/app.ts`, зараз `await handler`). Дедуп за `update_id` вже стоїть до обробника (Фаза 0): повтор від Telegram не запустить другого виклику (та сама картинка, надіслана вдруге, — новий апдейт і нова оплата, див. «Невідоме»). **Один дедлайн 25 с на весь конвеєр** (`AbortController`): `sendChatAction typing` → `getFile` → завантаження → base64 → виклик Anthropic. На платформі `waitUntil` після відповіді живе ≤ 30 с, тож решта (D1, `sendMessage`) має вкластися в ~5 с. Таймаут → «Не встиг розпізнати. Надішли фото ще раз» (N2), у `meals` **0 рядків**, облік — за правилом кроку 0.

**Фото.** Telegram віддає масив `PhotoSize` (стиснуте JPEG, довге ребро ≤ 1280). Беремо **найбільший елемент із `file_size ≤ 2 МБ`**; байти мають починатися з `FF D8 FF`, інакше «Не вдалося прочитати фото». `media_type` = `image/jpeg`. Картинка до 1280 px по довгому ребру ≈ 1,6 тис. візуальних токенів (28-пікселні патчі, [vision](https://platform.claude.com/docs/en/build-with-claude/vision), 2026-11-20; ліміти 10 МБ і 8000 px далекі). Власного зменшення немає (немає Images binding). До Anthropic йдуть **base64-байти**; URL файлу Telegram (містить токен) **ніде** не логується й не передається, помилки завантаження — лише статус (N7).

**Підпис-підказка.** `caption` (≤ 300, обрізається; «це 200 г гречки») іде в тезі `<user_caption>` як дані: підпис і текст на самій фото не змінюють правил і формату відповіді.

**Запит.** `@anthropic-ai/sdk` (`1.12.0` за `npm view` 2026-11-20, версія закріплена); `new Anthropic({ apiKey, maxRetries: 0 })` (повтори множать час і кошти); `messages.create({ model: FOOD_MODEL, max_tokens: FOOD_MAX_TOKENS, thinking: { type: "between_tools" }, output_config: { effort: "low", format: { type: "json_schema", schema } }, system, messages }, { signal })` — без `temperature`/`top_p`/prefill/`tool_choice` (на Sonnet 5.5 це 400). **`thinking` задаємо явно:** якщо його опустити, Sonnet 5.5 мислить адаптивно, а токени мислення їдять `max_tokens` (ризик `stop_reason: max_tokens` → INVALID, платно) і ціну; `between_tools` — це «мислення вимкнено», дозволене лише при `effort ≤ high`, без інших полів. 3.3 перевіряє на двох реальних фото, що API приймає `between_tools` разом із `output_config.format`; не приймає → `thinking` опустити, `FOOD_MAX_TOKENS = 2500` (стеля ≈ $0,03) і записувати `usage.output_tokens` у таблицю 5 фото. У `user`: блок `image` (base64), блок `text` — підпис і **список відомих назв** (`name_uk` з `foods`, ≤ 300: спершу `seed` за `id`, далі `ai_estimate` за кількістю використань у `meal_items`, потім за `id` — детермінований порядок): модель має брати назву дослівно, якщо продукт той самий — частіше збігається аліас. Вимоги до `system` (текст — 3.3, `src/ai/food-prompt.ts`): вага **приготованої страви на тарілці**; значення на 100 г — для того самого стану; назва — однина, називний, українською; ≤ 8 позицій; не їжа → `not_food: true`, `items: []`; невпевненість — у `confidence`, не в грамах.

**JSON-схема** (`additionalProperties: false`; чисельні межі `min/max` структурований вивід не підтримує — їх перевіряє код): `{ not_food: boolean, items: [{ name_uk: string, grams: number, kcal_100: number, protein_100: number, fat_100: number, carbs_100: number, confidence: "low"|"medium"|"high" }] }`, обидва поля `required`.

**Валідація (`parseFoodResponse`, чиста).** Перед розбором: `stop_reason` має бути `end_turn`; `max_tokens` / `refusal` → «не вдалося»; текстовий блок → `JSON.parse` у `try`. Далі: `not_food` або порожній `items` → **NOT_FOOD**; інакше кожна позиція: `name_uk` 1–60 після trim і непорожній `normalizeAlias`; `grams` скінченне 5–2000 (→ ціле); `kcal_100` 0–900; `protein/fat/carbs_100` 0–100 кожне, сума ≤ 100,5; **Атуотер:** `|kcal_100 − (4Б + 4В + 9Ж)| ≤ max(30, 0,3·kcal_100)`; `confidence` з переліку; позицій 1–8. Хоч одна позиція не пройшла → усе **INVALID** («Не вдалося розібрати відповідь. Спробуй ще раз», прийому немає). Межі інклюзивні.

**Зіставлення.** Для кожної позиції `findFoodByAlias(normalizeAlias(name_uk))`. Збіг → беремо **таблицю** (цифри моделі ігноруються). Немає → `insertEstimatedFood` (`source = ai_estimate`, значення моделі × 10, округлені) — ідемпотентно за аліасом: той самий продукт удруге береться з `foods`, нового рядка немає. Далі `createPendingMeal` одним batch (прийом + позиції; `status = pending`, `ai_raw_json`, `ai_model`).

**Не отруювати каталог.** скасування й прострочення `pending` видаляють `meal_items` прийому й **осиротілі** `ai_estimate`-продукти (без жодного `meal_items`) з аліасами: відкинута оцінка не стає еталоном; те саме робить крон для будь-яких осиротілих (збій між створенням продукту й прийому). Підтверджена лишається.

**Повідомлення** (`texts.ts`, HTML, `esc()` на назвах): `🍽 Рис варений ~180 г · 234 ккал`, рядок на позицію (`❓` при `low`, `🆕` для `ai_estimate`), підсумок `Разом: 520 ккал · Б 45 · Ж 12 · В 55` — **сума цілих значень позицій, кожне округлене за правилом знімка** `(grams·x_100 + 50) div 100`; та сама формула в прев'ю й у знімку, тож після `[Вірно]` число не змінюється. Кнопки `[✅ Вірно] [✏️ Грами] [❌ Скасувати]`. Те саме повідомлення редагується далі (`message_id` у `meals`).

**Кнопки** — `callback_data`: `m:y:<id>` · `m:g:<id>` · `m:x:<id>` (префікс `m:` вільний від `o:`, `s:` і дій потоку тренування; тест на унікальність префіксів). Усі дії — лише над прийомом **цього** `userId`.
- **✅ Вірно** → `confirmMeal`: один batch — `UPDATE meals SET status='confirmed' … WHERE id AND user_id AND status='pending'`, потім `UPDATE meal_items SET kcal, protein_dg, fat_dg, carbs_dg` для цього прийому (лише де знімок `NULL`, лише якщо прийом уже `confirmed`), значення за формулою вище (ціле, половина вгору). Друге натискання — 0 змін («Вже підтверджено»). Повідомлення змінюється на підсумок із рядком «Сьогодні: 1 450 / 2 480 ккал» (або без норми) і однією кнопкою `[🗑 Скасувати прийом]` (`m:x`) — щоб хибний тап не отруїв день.
- **✏️ Грами** → `await_grams_at = now` (знімає очікування в інших прийомів користувача), знімає `await_input` активного тренування, повідомлення просить: «Надішли грами через пробіл: 200 150» з нумерованим списком позицій (**за порядком показу** 1, 2, …; `position` у БД не перенумеровується, `parseGrams(text, n)` отримує n = кількість позицій, що лишилися).
- **❌ Скасувати** → `cancelMeal`: `pending` → `cancelled` (+ чистка каталогу вище); `confirmed` → `cancelled` (знімок і рядки лишаються для історії, у `dayTotals` не входять). Повторне — без помилки.

**Введення грамів.** Порядок маршрутизації тексту (доповнює `phase-2.md` §2): (1) reply на нагадування про вагу → **(1б) reply на питання про прогалину профілю** (`phase-3.md` §3) → (2) вага підходу тренування → **(2б) очікування грамів** → (3) анкета → (4) голе число… Очікування діє, якщо є `pending` прийом користувача з `await_grams_at` не старшим за `GRAMS_AWAIT_TTL` (15 хв); команда його знімає. `parseGrams(text, n)` (чиста): розділювачі — пробіл, `,`, `;`, новий рядок; токен `^\d{1,4}(г|g)?$`; значення 0–2000; кількість токенів = числу позицій. `0` = **вилучити позицію** (у показі решта нумерується наново); усі нулі — відмова. Помилка → підказка «Очікую 2 числа, отримав 1», очікування лишається. Успіх → `updateMealGrams` (лише власний `pending`), очікування знімається, повідомлення оновлюється.

**Прострочення.** `pending` старший за `MEAL_PENDING_TTL` (24 год від `created_at`): кнопки відповідають «Застаріло — надішли фото ще раз» (перевірка ледача, не залежить від крону) і не змінюють даних; крон у блоці прибирання Фази 1 переводить їх у `cancelled` з чисткою каталогу (`expirePendingMeals`), помилка не зупиняє інших кроків тіку. Підтвердження після 00:00 лягає на `meals.local_date` фото, а не дату тапу.

**Помилки API.** `429`, `5xx`, `overloaded`, обрив → «Сервіс розпізнавання зайнятий, спробуй за хвилину»; `401/403` → «Розпізнавання тимчасово недоступне» + лог без ключа (N9); `400` → як INVALID. Повторів немає. Облік — за кроком 0: відповідь `200` → `settleAiUsage` з `usage` завжди (навіть якщо потім INVALID); HTTP-помилка → `releaseAiUsage`; обрив після відправки → оцінка лишається.

## 2. ШІ: модель, ціни, ліміт

`src/config.ts` (код не має числових літералів моделей і цін): `FOOD_MODEL = "claude-sonnet-5-5"`; ціни — `P_in/P_out` у µUSD за 1 млн токенів; ліміти.

| Модель | Вхід | Вихід | Де |
|---|---|---|---|
| `claude-sonnet-5-5` | $2 / MTok → `2 000 000` | $10 / MTok → `10 000 000` | **Фото їжі (3.3)** |
| `claude-haiku-5-5` | $0,10 (промпт > 100 тис. — $0,50) | $0,50 (далі $2,50) | чат, Фаза 4 |

Ціни звірено живцем ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)) **2026-11-20**; 3.3 звіряє ще раз перед коммітом.

**Одне фото:** вхід ≈ 1,6 тис. (картинка) + ≈ 1,5 тис. (промпт, список назв) ≈ $0,006; вихід (мислення вимкнено) 400–700 токенів ≈ $0,005; **типово ≈ $0,01**, стеля `max_tokens` → ≈ $0,02. **`AI_DAILY_LIMIT_MICRO = 300 000`** ($0,30/день, план). **`FOOD_CALL_EST_MICRO = 15 000`** — оцінка-резервування (більша за типову, тож ліміт трохи консервативний: ≈ 20 фото на день). Місяць ≈ $1–2 (N10); $5/міс у Console — друга, зовнішня огорожа. Інші константи в `config.ts`: `FOOD_TIMEOUT_MS = 25 000`, `FOOD_MAX_TOKENS = 1500`, `FOOD_MAX_ITEMS = 8`, `MEAL_PENDING_TTL_MS`, `GRAMS_AWAIT_TTL_MS`.

**Секрети — один пакет у 3.3** (👤, ключ вводить лише людина; агент його не друкує, N7): `wrangler secret put ANTHROPIC_API_KEY` для preview **і** production + ліміт $5/міс у Anthropic Console + підтвердження. 3.5 лише перевіряє наявність (`wrangler secret list`, без значення).

`fallbacks` для `refusal` **не вмикаємо** (**[П]**): для їжі відмова рідкісна, показуємо «не вдалося»; скіл `claude-api` радить їх за замовчуванням — 3.3 згадує це рішення в PR.

## 3. Історії

Кожна окремо тестована; клієнт Anthropic — мок, реальних викликів у тестах немає.
**P3.3 — Фото (3.3).** Клієнт Anthropic — мок; реальних викликів у тестах немає.
1. **Given** валідна відповідь з двома відомими продуктами, **Then** `pending`-прийом із двома позиціями, цифри з таблиці (не з моделі), кнопки; ліміт не вичерпано → клієнт викликано 1 раз.
2. **Given** невідомий продукт, **Then** `foods` `ai_estimate` + аліас; **When** те саме фото вдруге, **Then** нового `foods` немає.
3. **Given** `not_food`, не-JSON, `max_tokens`/`refusal`, `kcal_100 = 901`, `grams = 4`, порушений Атуотер, 9 позицій → **Then** текст, **0 рядків `meals`**; межі `900`, `5`, `2000`, 8 позицій проходять.
4. **Given** мок не відповідає 25 с після відправки, **Then** «Не встиг…», 0 `meals`, у `ai_usage` лишається `FOOD_CALL_EST_MICRO`; **Given** дедлайн спрацював на `getFile` (до відправки), **Then** резервування знято; **Given** 429, **Then** текст «зайнятий», резервування знято. (Мутант: без `AbortController` → червоний.)
5. **Given** залишок ліміту на 2 резервування й альбом з 10 фото в паралельних апдейтах, **Then** клієнт викликано ≤ 2 рази, решта — текст ліміту. (Мутант: прибрати резервування або перевіряти суму окремо від `INSERT` → червоний.) **Given** відповідь `200`, **Then** `ai_usage` оновлено фактичними токенами й ціною, не оцінкою.
6. **Given** запит до Anthropic, **Then** у тілі й логах немає `api.telegram.org` і токена бота, зображення — `base64`. (Мутант: URL замість base64 → червоний.)
7. **Given** `[✅ Вірно]` двічі, **Then** один перехід, знімок записано один раз, друге — «Вже підтверджено»; **Given** щойно розпізнане фото, **Then** прийом `pending`, не `confirmed` (мутант: автопідтвердження → червоний).
8. **Given** `[✏️ Грами]` і `200 150` / `200,150` / `150г 0` для 2 позицій, **Then** грами оновлено / позицію вилучено; `200`, `0 0`, `abc`, `2001` → підказка, очікування лишається, дані без змін; **Given** відкрите очікування ваги підходу, **When** `[✏️ Грами]`, **Then** текст іде в грами.
9. **Given** `[❌ Скасувати]` і новий `ai_estimate` лише в цьому прийомі, **Then** `cancelled`, `foods` з цим продуктом немає; **Given** підтверджений, потім `m:x`, **Then** `cancelled`, у `dayTotals` немає.
10. **Given** `pending` старший за 24 год, **When** `[✅ Вірно]`, **Then** «Застаріло», дані без змін; **When** крон, **Then** `cancelled` + чистка каталогу.
11. **Given** фото о 23:50 і підтвердження о 00:10, **Then** прийом на `local_date` фото.
12. **Given** немає `ANTHROPIC_API_KEY`, **Then** «не підключене», без виклику й `ai_usage`.
13. **Given** запит до Anthropic, **Then** `thinking = { type: "between_tools" }`, `effort = "low"`, немає `temperature`/`top_p`/prefill/`tool_choice`, `maxRetries = 0`.
14. **Given** прев'ю «Разом» для 8 позицій і потім `[Вірно]`, **Then** число збігається (одна формула округлення).
15. **Given** `[✏️ Грами] 0 150 0` для 3 позицій, **Then** лишилась одна, у наступному `[✏️ Грами]` — «1 число».
