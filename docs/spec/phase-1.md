# Фаза 1 — Тренування в залі

## Задача

У залі власник відкриває `/trening`, бачить вправу з призначеною вагою й записує типовий підхід одним натисканням. Наступне призначення бот рахує сам за правилами подвійної прогресії, без ШІ.

**Готово, коли** реальна тренування в залі записана на preview-боті з ≤ 1 натисканням на типовий підхід, а призначення наступної збіглося з таблицею правил.

## Схема (міграція фази 1)

Таблиці пізніших фаз (`body_weights`, `reminders_sent`, їжа, ШІ) тут не створюються. Ваги — `REAL` кг; арифметика кроків — у цілих грамах.

**`exercises`** — каталог, спільний для всіх (без `user_id`)

| Поле | Тип | Обмеження |
|---|---|---|
| `id` | INTEGER | PK |
| `slug` | TEXT | NOT NULL UNIQUE, латиниця kebab-case |
| `name_uk` | TEXT | NOT NULL |
| `equipment` | TEXT | NOT NULL CHECK IN (`barbell`,`dumbbell`,`machine`,`cable`,`bodyweight`) |
| `weight_step_kg` | REAL | NOT NULL |
| `min_weight_kg` | REAL | NOT NULL CHECK ≥ 0 |
| `muscle_group` | TEXT | NOT NULL CHECK IN (`legs`,`chest`,`back`,`shoulders`,`core`) |
| `cues_uk` | TEXT | NOT NULL — рівно 3 рядки через `\n` |
| `video_url` | TEXT | NULL (зарезервовано) |

CHECK рядка: `(equipment = 'bodyweight' AND weight_step_kg = 0 AND min_weight_kg = 0) OR (equipment <> 'bodyweight' AND weight_step_kg > 0)`.

**`exercise_substitutes`** — `exercise_id` FK, `substitute_id` FK; PK (`exercise_id`,`substitute_id`); CHECK `exercise_id <> substitute_id`. Пара напрямлена: «чим замінити X».

**`programs`** — `id` PK, `user_id` FK `users` NOT NULL, `name` TEXT NOT NULL, `active` INTEGER NOT NULL CHECK IN (0,1), `created_at` NOT NULL. Частковий UNIQUE INDEX `programs_one_active` ON (`user_id`) WHERE `active = 1`.

**`program_days`** — `id` PK, `program_id` FK NOT NULL, `code` TEXT NOT NULL CHECK `length(code) BETWEEN 1 AND 8`, `position` INTEGER NOT NULL; UNIQUE (`program_id`,`code`), UNIQUE (`program_id`,`position`).

**`program_exercises`** (слот) — `id` PK, `program_day_id` FK NOT NULL, `exercise_id` FK NOT NULL, `position` NOT NULL, `sets` CHECK 1–10, `rep_min` CHECK ≥ 1, `rep_max` CHECK `rep_max >= rep_min AND rep_max <= 50`; UNIQUE (`program_day_id`,`position`), UNIQUE (`program_day_id`,`exercise_id`).

**`workouts`**

| Поле | Тип | Обмеження |
|---|---|---|
| `id` · `user_id` · `program_day_id` | INTEGER | PK · FK `users` NOT NULL · FK NOT NULL |
| `status` | TEXT | NOT NULL CHECK IN (`active`,`done`,`abandoned`) |
| `started_at` / `finished_at` | INTEGER | NOT NULL / NULL, UTC мс |
| `effort` | INTEGER | NULL, CHECK 1–5 |
| `note` | TEXT | NULL (не використовується у фазі 1) |
| `await_input` | TEXT | NULL — JSON стану очікування ваги (див. «Введення ваги») |

CHECK рядка: `(status = 'active') = (finished_at IS NULL)`; `(status = 'done') = (effort IS NOT NULL)`; `await_input IS NULL OR status = 'active'`.
Частковий UNIQUE INDEX `workouts_one_active` ON (`user_id`) WHERE `status = 'active'`. Індекси: (`user_id`,`started_at`) — історія; (`status`,`started_at`) — крон.

**`workout_sets`**

| Поле | Тип | Обмеження |
|---|---|---|
| `id` · `workout_id` | INTEGER | PK · FK NOT NULL |
| `program_exercise_id` | INTEGER | FK NOT NULL — слот підходу (заміна, продовження) |
| `exercise_id` | INTEGER | FK NOT NULL — фактично виконана вправа |
| `set_no` | INTEGER | NOT NULL CHECK 1–10 |
| `weight_kg` / `reps` | REAL / INTEGER | NULL, якщо пропущено |
| `prescribed_weight_kg` / `prescribed_reps` | REAL / INTEGER | NOT NULL — знімок призначення |
| `skipped` | INTEGER | NOT NULL DEFAULT 0 CHECK IN (0,1) |

CHECK рядка: `(skipped = 1 AND weight_kg IS NULL AND reps IS NULL) OR (skipped = 0 AND weight_kg >= 0 AND reps BETWEEN 0 AND 50)`.
**UNIQUE (`workout_id`,`exercise_id`,`set_no`)** — повторне натискання = upsert `ON CONFLICT … DO UPDATE`, не дубль. Індекс (`exercise_id`,`workout_id`) — історія вправи.

**Ізоляція.** Чужий чи неіснуючий `workout` для `repo` → `null` при читанні, «не знайдено» без змін при записі (не виняток). Каталог — спільний, лише читання.

## Правила прогресії

`nextPrescription(history, exercise, slot) → { weightKg, targetReps, reason }` — чиста функція.

**Вхід.** `history` — сесії цієї вправи з тренувань `done` і `abandoned`, від старшої до новішої; у кожній — підходи (`set_no`, вага, повтори, `skipped`), заплановані `sets` слота й `effort` тренування. Сесія без жодного непропущеного підходу не зараховується (її немов немає). Відсутні підходи (тренування обірвалось) рахуються як пропущені. Діапазон `rep_min`–`rep_max` — зі слота, крок і мінімум — з вправи.

**Означення для зарахованої сесії:**
- **повна** — робочих підходів стільки, скільки `sets`, без пропущених і без підходів іншої ваги;
- **успіх** — повна й кожен робочий підхід ≥ `rep_max`;
- **невдача** — хоч один робочий підхід < `rep_min`. Пропущений підхід — не невдача;
- `норм(x)` = `max(min_weight_kg, ⌊x / крок⌋ × крок)`; для кроку 0 — `max(min_weight_kg, x)`.

**Правила** (перевіряються в цьому порядку, спрацьовує перше):

| № | Умова | Призначення | `reason` |
|---|---|---|---|
| 1 | немає зарахованих сесій | `min_weight_kg` × `rep_min` | `calibration` |
| 4 | дві останні сесії — невдачі з однаковою W | `норм(W × 0,9)` × `rep_min` | `deload` |
| 5 | остання — успіх, її `effort = 5`, і передостання не була «успіх при тій самій W з `effort = 5`» | W × `rep_max` | `hold` |
| 2 | остання — успіх | `норм(W + крок)` × `rep_min`; крок 0 → W × `rep_max` (стеля) | `increase` |
| 3 | інакше | W × `clamp(макс. повтори робочих + 1, rep_min, rep_max)` | `reps` |
| 6 | завжди, після обраного правила | вага кратна кроку й ≥ `min_weight_kg` — через `норм` | — |

Наслідки: лічильник невдач — лише поспіль і лише за тієї самої W, тож сесія без невдачі між ними й розвантаження (W змінилась) його скидають. Утримання (5) — не двічі поспіль. `effort = NULL` (`abandoned`) ≠ 5.

## Історії

Історії потоку (P1.3–P3.1) — у [phase-1-flow.md](phase-1-flow.md).

### P1.1 — Каталог, програма й схема в БД

**Навіщо:** обмеження в БД ловлять помилки коду, яких тест не передбачив.
**Незалежно тестована:** міграція + сид у pool workers.

1. **Given** чиста D1, **When** міграція й сид, **Then** 18 вправ, пари замін за таблицею каталогу, одна активна програма з днями A/B і слотами за таблицею програми.
2. **Given** сид уже виконано, **When** сид удруге, **Then** кількість рядків кожної таблиці та сама.
3. **Given** активна програма, **When** вставка другої `active = 1` для того самого `user_id`, **Then** помилка обмеження. Те саме — для другого `active`-тренування.
4. **Given** `workout_sets` з `skipped = 1` і `reps = 8`, **When** вставка, **Then** помилка CHECK. Те саме для `status = 'done'` без `effort`, `bodyweight` з кроком 2,5, `rep_max < rep_min`.
5. **Given** тренування користувача A, **When** `repo` з `userId` B читає чи пише його, **Then** `null` / «не знайдено», рядок не змінено.
6. **Given** `upsertSet` двічі з тим самим (`workout_id`,`exercise_id`,`set_no`), друге — з іншими повторами, **When** читання, **Then** один рядок з останніми значеннями (відмову застарілій кнопці робить потік, не `repo`).

### P1.2 — Рушій прогресії

**Навіщо:** вагу рахує код, а не модель, — тут головна цінність і головний ризик продукту.
**Незалежно тестована:** table-driven тест без БД і Telegram.

1. **Given** кожен рядок таблиці «історія → призначення», **When** `nextPrescription`, **Then** вага, повтори й правило — як у рядку (номер рядка — у назві тесту).
2. **Given** будь-який вхід із рядків таблиці, **When** результат, **Then** вага кратна кроку й ≥ `min_weight_kg`.
3. **Given** `done`-тренувань немає / останнє `done` — A / останнє `done` — B, а пізніше є `abandoned` A, **When** `nextDayCode`, **Then** A / B / A.
