## 1. Модель даних

Одна міграція **3.1** (`0007`, номер — наступний за наявним) створює шість таблиць. Друга міграція **3.4** перебудовує `reminders_sent` (розділ 4). Час — UTC мс; «локальна дата» — `YYYY-MM-DD` за `users.tz` на момент запису; доступ — лише `src/db/repo.ts`, `userId` у кожній функції над рядками користувача (N8). `foods` і `food_aliases` — **спільний каталог без `user_id`**, як `exercises` (виняток без `userId`, як у `repo.ts`). CHECK — і в `schema.ts`, і в SQL (нові таблиці).

**Одиниці.** Макроси — **десяті грама** (`_dg`), ккал — цілі, як `weight_dg` у Фазі 2: суми цілі, без дрейфу `float`.

**`foods`**: `id` INTEGER PK; `name_uk` TEXT 1–60 символів; `kcal_100` INTEGER 0–900; `protein_100_dg`, `fat_100_dg`, `carbs_100_dg` INTEGER 0–1000 (на 100 г); `source` IN (`seed`,`ai_estimate`,`manual`); `fdc_ref` TEXT NULL (номер у джерелі сиду); `created_at`. CHECK: `protein+fat+carbs ≤ 1000` дг.

**`food_aliases`**: `alias` TEXT PK (**лише** результат `normalizeAlias`, розділ 2); `food_id` → `foods.id` ON DELETE CASCADE. Інваріант: кожен `foods.name_uk` має аліас `normalizeAlias(name_uk)`.

**`meals`**: `id` INTEGER PK AUTOINCREMENT; `user_id`; `status` IN (`pending`,`confirmed`,`cancelled`); `eaten_at` UTC мс (= `message.date` фото × 1000); `local_date` (за `tz` на цей момент, **не змінюється** після); `photo_file_id` TEXT NULL (file_id Telegram — токена не містить); `caption` TEXT NULL ≤ 300; `ai_model` TEXT; `ai_raw_json` TEXT ≤ 8192 (сира відповідь моделі, без картинки); `message_id` INTEGER NULL (повідомлення бота з кнопками); `await_grams_at` INTEGER NULL (очікуємо введення грамів, `phase-3-photo.md`); `created_at`; `confirmed_at` NULL. Індекс (`user_id`,`local_date`,`status`).

**`meal_items`**: `meal_id` → `meals.id` ON DELETE CASCADE; `position` 1–8; PK (`meal_id`,`position`); `food_id` → `foods.id`; `grams` INTEGER 1–2000; `confidence` IN (`low`,`medium`,`high`); **знімок** `kcal`, `protein_dg`, `fat_dg`, `carbs_dg` INTEGER ≥ 0, **усі чотири NULL або усі чотири не NULL** (CHECK). Поки прийом `pending` — знімка немає (показ рахується з `foods` наживо); `confirmMeal` пише його, правка `foods` потім історію не чіпає.

**`nutrition_targets`**: `user_id`; `valid_from` TEXT (локальна дата); PK (`user_id`,`valid_from`); `kcal` 800–6000; `protein_g`, `fat_g`, `carbs_g` ≥ 0 (цілі грами); `reason` IN (`formula`,`trend`,`manual`); `source_date` TEXT NULL (для `trend` — дата пропозиції); `created_at`. Частковий `UNIQUE (user_id, source_date) WHERE source_date IS NOT NULL`. **Чинна норма на дату D** = рядок з максимальним `valid_from ≤ D`. `manual` зарезервовано (команди зміни норми немає — «Поза межами»).

**`ai_usage`**: `id`; `user_id`; `model`; `input_tokens`, `output_tokens` ≥ 0; `cost_micro` INTEGER ≥ 0 (мільйонні частки USD: $0,01 = 10 000); `purpose` TEXT 1–32 (`food_photo`; **без закритого CHECK**, щоб Фаза 4 додала `chat` без перебудови таблиці); `local_date`; `created_at`. Індекс (`user_id`,`local_date`). Рядок — **резервування, що стає фактом**: створюється до виклику з оцінкою, після відповіді оновлюється фактичною ціною (`phase-3-photo.md`, §1 «Крок 0»).

**Вартість:** `cost_micro = ⌈(input·P_in + output·P_out) / 1 000 000⌉`, де `P_*` — мікродолари за 1 млн токенів з `src/config.ts` (`phase-3-photo.md` §2); токени кешу не враховуємо (кешу немає).

**repo (3.1):** `findFoodByAlias`; `insertEstimatedFood` — ідемпотентно за аліасом (конфлікт → наявний `foods`, не другий); `createPendingMeal` одним batch; `confirmMeal`; `updateMealGrams`; `cancelMeal`; `getMeal`; `awaitingGramsMeal`; `dayTotals(userId, localDate)` — **лише `confirmed`**, суми зі знімка; `reserveAiUsage` (умовний атомарний `INSERT … SELECT`, повертає id або `null` при перевищенні ліміту), `settleAiUsage`, `releaseAiUsage`, `aiSpendToday(userId, localDate)`; `expirePendingMeals`; `getTargetOn`, `insertTarget`. ## 3. Норма КБЖУ (3.2)

Чисті функції `src/domain/nutrition.ts`, без I/O й `Date.now` (рік — параметром).

**Вхід:** `sex` (`m`/`f`), `birth_year`, `height_cm`, `activity`, `goal`, вага. **Вага для норми** = «Зараз» Фази 2 (середнє `W0`, інакше останній запис `body_weights`), а немає записів — `user_profiles.weight_kg`. Вік = `рік(локальна дата) − birth_year` (похибка ≤ 1 рік ≈ ≤ 1 % ккал).

**Формули:**
- `BMR = 10·w + 6,25·h − 5·вік + (m: +5 · f: −161)` (Міффлін — Сан Жеор), `w` кг, `h` см; не округлюється.
- `TDEE = BMR · k`: `low` 1,375 · `mid` 1,55 · `high` 1,725 (`activity` — рух **поза залом**, тренування вже враховані).
- `kcal = round₁₀(TDEE · (1 + Δ))` — до найближчих 10 ккал, половина вгору. Δ за `goal`: `lose_fat` −20 % · `recomp` **−10 %** (рішення плану) · `muscle` +10 % · `strength`, `health`, `other` 0.
- `білок = round(1,8·w)` г · `жир = round(0,8·w)` г · `вуглеводи = max(0, round((kcal − 4·білок − 9·жир)/4))`. Якщо `4Б + 9Ж > kcal` — `вуглеводи = 0` і `kcal = 4Б + 9Ж` (норма лишається арифметично цілісною).

**Контрольні вектори (тести 3.2, рік 2026):** `m`, 80 кг, 180 см, 1996, `mid`, `recomp` → BMR 1780, **2480** ккал, Б 144, Ж 64, В 332. `f`, 60 кг, 165 см, 1996, `low`, `recomp` → BMR 1320,25, **1630**, Б 108, Ж 48, В 192. `f`, 150 кг, 150 см, 1946, `low`, `lose_fat` → 2060 за формулою < 4Б+9Ж = 2160 → **2160**, Б 270, Ж 120, В 0.

**Коли рахувати й питати.** Норма створюється **ліниво**: при першому `/yizha` і (мовчки, без питань) при `[✅ Вірно]`, якщо рядків `nutrition_targets` ще немає і профіль повний → рядок `valid_from = сьогодні`, `reason = formula`. Фото й підтвердження **працюють без норми** (лише сума). Потрібні: `goal`, `sex`, `birth_year`, `height_cm`, `activity`, вага (профіль або `body_weights`). Анкета 1b дозволяє «Пропустити», тож прогалини реальні. Бракує — `/yizha` ставить **одне** питання про перше відсутнє поле (`goal → sex → birth_year → height_cm → activity → вага`) **окремим повідомленням**, не через анкету 1b (її єдиний вхід — «Пройти знову» з першого питання до нового плану, що ще й скидає дні нагадувань) і без змін `onboarding_state`:
- `goal`, `sex`, `activity` — кнопки `f:go:<значення>` · `f:sx:<m|f>` · `f:ac:<low|mid|high>` (значення enum як у профілі; префікс `f:` вільний від `o:`, `s:`, `m:`, `n:` і дій тренування), підписи — з `texts.ts` анкети;
- `birth_year`, `height_cm`, `weight_kg` — число **у reply** на питання; питання впізнається за заголовком тексту повідомлення, на яке відповідають (константи в `texts.ts`, стан не потрібен); межі ті самі, що в анкеті: 1930–2020 / 120–230 / 30–300, інакше підказка й нічого не пишеться. Reply займає в маршрутизації тексту місце (1б) одразу після reply на нагадування про вагу.

Відповідь пишеться наявним оновленням профілю в `repo.ts` (3.2 обирає функцію), далі — наступне бракуюче або підсумок. Заповнене поле не питається вдруге (P3.2.5). Якщо за формулою `kcal` поза 800–6000 (крайній, але дозволений профіль: 30 кг, 120 см, 1930 → ≈ 450) — норму **не створюємо**, `/yizha` каже «Перевір профіль: норма виходить за межі 800–6000 ккал» і показує суму.

Профіль змінився → норма **не** перераховується сама (**[П]**): норма — домовленість із датою; змінює її лише тренд (розділ 4). `/yizha` показує «норма від 20.11».

**`/yizha` (3.2)** — підсумок **сьогоднішньої локальної дати**: рядок `З'їдено 1 450 / 2 480 ккал (58 %)`; нижче `Б 98 / 144 г · Ж 40 / 64 г · В 160 / 332 г`; список підтверджених прийомів за день (час за `tz`, позиції, ккал) — не більше 12, далі «…ще N»; рядок `⏳ Не підтверджено: N` (pending за сьогодні, **не в сумі**); перебір — `+120 ккал понад норму`; без норми (бракує полів) — питання вище, суму показуємо. Норма береться **чинна на цю дату** (`getTargetOn`), не найновіша. Текст ≤ 4096 (N6). `yizha` — у `BOT_COMMANDS` («Їжа за день і норма»).

## 4. Корекція норми за трендом (3.4)

Раз на 14 днів код порівнює вагу з цілью й пропонує ±100 ккал. Усе — за локальними датами; вікна `W0` (сьогодні−6…сьогодні) і `W1` (попередні 7) — **ті самі**, що на екранах Фази 2.

**Коли оцінювати.** Крон, для користувача з чинною нормою, у вікні тіків `[09:00, 10:00)` за `tz` (`TREND_LOCAL_MINUTES = 540`, вікно 60 хв, як у Фази 2). Умови, усі разом: (а) `сьогодні − max(valid_from чинної норми, дата останньої пропозиції trend у reminders_sent) ≥ 14`; (б) зважувань у `W0 ∪ W1` **≥ 10**, у кожному вікні **≥ 3**; (в) є пропозиція за порогами нижче. Не виконано (а) або (б) — тихо, без заявки (завтра перевіримо знову); (в) не виконано — теж тихо, цикл не спалюється. Якщо надіслано — заявка `reminders_sent (user, 'trend', дата)` (заявити → надіслати → при помилці зняти, як у Фазі 2).

**Темп:** `p = (avg(W0) − avg(W1)) / avg(W1) · 100` %/тиждень — точною цілочисельною арифметикою (перехресне множення десятих кг, без `float`). Пороги — таблиця `GOAL_BANDS` у `config.ts`: смуга `[lo, hi]` %/тиж; шум середніх за 3–7 зважувань ≈ ±0,25 %, тож додано запас `m = 0,20`:

| `goal` | смуга | `+100 ккал`, якщо `p <` | `−100 ккал`, якщо `p >` |
|---|---|---|---|
| `lose_fat` | −1,0 … −0,5 | −1,20 | −0,30 |
| `recomp` | −0,25 … 0 | **−0,45** | **+0,20** |
| `muscle` | +0,1 … +0,5 | −0,10 | +0,70 |
| `strength`, `health`, `other` | −0,25 … +0,25 | −0,45 | +0,45 |

Межі **строгі**: рівно на порозі — «нічого». Запобіжники: сумарне відхилення від `formula`-норми ≤ ±300 ккал (далі пропозиції немає); нова норма ≥ 1200 ккал. `+100` ккал → вуглеводи +25 г; `−100` → −25 г і **лише якщо вуглеводи були ≥ 25 г** (інакше пропозиції немає: норма лишається `kcal ≈ 4Б+4В+9Ж`); білок і жир не змінюються.

**Міграція 3.4 перебудовує `reminders_sent`:** `reminders_sent_kind` — table-level CHECK (`0005`), тож SQLite не розширить його через `ALTER`: нова таблиця з `kind IN (train, weigh, report, trend)` → копія рядків → `DROP` → `RENAME`. Тест: рядки збережені, `trend` приймається. Бекап перед prod — `backup:prod` у 3.5.

**Повідомлення:** `📈 За 14 днів: 80,0 → 79,4 кг (−0,75 %/тиж) — швидше, ніж треба для цілі. Пропоную 2480 → 2580 ккал (вуглеводи +25 г). [✅ Прийняти] [Ні]`. Кнопки: `n:a:<±100>:<YYYYMMDD>` і `n:d:<YYYYMMDD>` (дельта й дата пропозиції — у даних).

**Прийняття — умовний `INSERT … SELECT … WHERE NOT EXISTS`** одним оператором (атомарно): новий рядок `nutrition_targets` (`valid_from` = сьогодні, `reason = trend`, `source_date` = дата пропозиції, ккал = чинна + дельта) створюється, лише якщо (1) для цієї `source_date` рядка ще немає (частковий UNIQUE) і (2) після дати пропозиції не було ні нового `trend` у `reminders_sent`, ні нового `valid_from` у `nutrition_targets` — інакше «Пропозиція застаріла». Повторне натискання → 0 нових рядків, «Вже застосовано». `[Ні]` лише знімає кнопки; цикл уже обліковано заявкою.
