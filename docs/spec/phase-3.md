# Фаза 3 — Харчування за фото

## Стан

**Оновлено:** 2026-11-20 · **Зріз:** специфікація Фази 3 (завдання 3.0) · **Читають:** 3.1–3.5 разом із `00-common.md`; 3.2 — розділи 3 і 4, 3.4 — розділ 6.
**Спирається на:** 1b (профіль: `sex`, `birth_year`, `height_cm`, `weight_kg`, `activity`, `goal`) і 2 (`body_weights`, «Зараз» і вікна `W0/W1`, `reminders_sent`, крон `*/15`, `users.tz`) — онбординг і вагу Фаза 3 **не збирає вдруге**. Припущення — у «Невідоме» (**[П]**). Блокуючих питань немає; джерело сиду (розділ 2) підтверджено власником 2026-11-20.

## Задача

Фото тарілки → Claude (`claude-sonnet-5-5`) повертає «продукт + грами» → КБЖУ з таблиці продуктів → людина підтверджує кнопкою → `/yizha` показує день проти норми. Норму рахує код з профілю; раз на 14 днів пропонує ±100 ккал за трендом ваги. ШІ лише розпізнає, запис — код після кнопки. Денний ліміт витрат на ШІ — жорсткий.

## 1. Модель даних

Одна міграція **3.1** (`0007`, номер — наступний за наявним) створює шість таблиць. Друга міграція **3.4** розширює CHECK `reminders_sent.kind` (розділ 6). Час — UTC мс; «локальна дата» — `YYYY-MM-DD` за `users.tz` на момент запису; доступ — лише `src/db/repo.ts`, `userId` у кожній функції над рядками користувача (N8). `foods` і `food_aliases` — **спільний каталог без `user_id`**, як `exercises` (виняток без `userId`, як у `repo.ts`). CHECK — і в `schema.ts`, і в SQL (нові таблиці).

**Одиниці.** Макроси — **десяті грама** (`_dg`), ккал — цілі, як `weight_dg` у Фазі 2: суми цілі, без дрейфу `float`.

**`foods`**: `id` INTEGER PK; `name_uk` TEXT 1–60 символів; `kcal_100` INTEGER 0–900; `protein_100_dg`, `fat_100_dg`, `carbs_100_dg` INTEGER 0–1000 (на 100 г); `source` IN (`seed`,`ai_estimate`,`manual`); `fdc_ref` TEXT NULL (номер у джерелі сиду); `created_at`. CHECK: `protein+fat+carbs ≤ 1000` дг.

**`food_aliases`**: `alias` TEXT PK (**лише** результат `normalizeAlias`, розділ 2); `food_id` → `foods.id` ON DELETE CASCADE. Інваріант: кожен `foods.name_uk` має аліас `normalizeAlias(name_uk)`.

**`meals`**: `id` INTEGER PK AUTOINCREMENT; `user_id`; `status` IN (`pending`,`confirmed`,`cancelled`); `eaten_at` UTC мс (= `message.date` фото × 1000); `local_date` (за `tz` на цей момент, **не змінюється** після); `photo_file_id` TEXT NULL (file_id Telegram — токена не містить); `caption` TEXT NULL ≤ 300; `ai_model` TEXT; `ai_raw_json` TEXT ≤ 8192 (сира відповідь моделі, без картинки); `message_id` INTEGER NULL (повідомлення бота з кнопками); `await_grams_at` INTEGER NULL (очікуємо введення грамів, розділ 4); `created_at`; `confirmed_at` NULL. Індекс (`user_id`,`local_date`,`status`).

**`meal_items`**: `meal_id` → `meals.id` ON DELETE CASCADE; `position` 1–8; PK (`meal_id`,`position`); `food_id` → `foods.id`; `grams` INTEGER 1–2000; `confidence` IN (`low`,`medium`,`high`); **знімок** `kcal`, `protein_dg`, `fat_dg`, `carbs_dg` INTEGER ≥ 0, **усі чотири NULL або усі чотири не NULL** (CHECK). Поки прийом `pending` — знімка немає (показ рахується з `foods` наживо); `confirmMeal` пише його, правка `foods` потім історію не чіпає.

**`nutrition_targets`**: `user_id`; `valid_from` TEXT (локальна дата); PK (`user_id`,`valid_from`); `kcal` 800–6000; `protein_g`, `fat_g`, `carbs_g` ≥ 0 (цілі грами); `reason` IN (`formula`,`trend`,`manual`); `source_date` TEXT NULL (для `trend` — дата пропозиції); `created_at`. Частковий `UNIQUE (user_id, source_date) WHERE source_date IS NOT NULL`. **Чинна норма на дату D** = рядок з максимальним `valid_from ≤ D`. `manual` зарезервовано (команди зміни норми немає — «Поза межами»).

**`ai_usage`**: `id`; `user_id`; `model`; `input_tokens`, `output_tokens` ≥ 0; `cost_micro` INTEGER ≥ 0 (мільйонні частки USD: $0,01 = 10 000); `purpose` TEXT 1–32 (`food_photo`; **без закритого CHECK**, щоб Фаза 4 додала `chat` без перебудови таблиці); `local_date`; `created_at`. Індекс (`user_id`,`local_date`).

**Вартість:** `cost_micro = ⌈(input·P_in + output·P_out) / 1 000 000⌉`, де `P_*` — мікродолари за 1 млн токенів з `src/config.ts` (розділ 5); токени кешу не враховуємо (кешу немає).

**repo (3.1):** `findFoodByAlias`; `insertEstimatedFood` — ідемпотентно за аліасом (конфлікт → наявний `foods`, не другий); `createPendingMeal` одним batch; `confirmMeal`; `updateMealGrams`; `cancelMeal`; `getMeal`; `awaitingGramsMeal`; `dayTotals(userId, localDate)` — **лише `confirmed`**, суми зі знімка; `recordAiUsage`; `aiSpendToday(userId, localDate)`; `expirePendingMeals`; `getTargetOn`, `insertTarget`. Чужий `userId` → `null`/`false`, без змін.

## 2. Каталог продуктів і сид

**`normalizeAlias(s)`** — чиста, `src/domain/text.ts`: (1) NFC; (2) `toLowerCase()`; (3) **прибрати** апострофи `'` `ʼ` `’` `‘` `` ` `` `´` `′` (м'ясо = мʼясо = мясо); (4) усе, що не літера й не цифра (`\p{L}\p{N}`), — у пробіл; (5) стиснути пробіли, обрізати. Порожній результат — недійсний (відмова). Приклади (тести): `М’ЯСО  свиняче` → `мясо свиняче`; `Куряче філе (варене)` → `куряче філе варене`; `Йогурт-грецький` → `йогурт грецький`.

**Сид ≈ 100 продуктів** (`source = seed`): прості продукти й інгредієнти (крупи й макарони — варені, м'ясо й риба — приготовані, яйця, молочне, хліб, овочі, фрукти, горіхи, олії, солодке) — без складних страв. Страв (борщ, вареники) у сиді **навмисно** немає: джерело їх не має, вигадані цифри гірші за оцінку моделі — їх покриває `ai_estimate`. ## 3. Норма КБЖУ (3.2)

Чисті функції `src/domain/nutrition.ts`, без I/O й `Date.now` (рік — параметром).

**Вхід:** `sex` (`m`/`f`), `birth_year`, `height_cm`, `activity`, `goal`, вага. **Вага для норми** = «Зараз» Фази 2 (середнє `W0`, інакше останній запис `body_weights`), а немає записів — `user_profiles.weight_kg`. Вік = `рік(локальна дата) − birth_year` (похибка ≤ 1 рік ≈ ≤ 1 % ккал).

**Формули:**
- `BMR = 10·w + 6,25·h − 5·вік + (m: +5 · f: −161)` (Міффлін — Сан Жеор), `w` кг, `h` см; не округлюється.
- `TDEE = BMR · k`: `low` 1,375 · `mid` 1,55 · `high` 1,725 (`activity` — рух **поза залом**, тренування вже враховані).
- `kcal = round₁₀(TDEE · (1 + Δ))` — до найближчих 10 ккал, половина вгору. Δ за `goal`: `lose_fat` −20 % · `recomp` **−10 %** (рішення плану) · `muscle` +10 % · `strength`, `health`, `other` 0.
- `білок = round(1,8·w)` г · `жир = round(0,8·w)` г · `вуглеводи = max(0, round((kcal − 4·білок − 9·жир)/4))`. Якщо `4Б + 9Ж > kcal` — `вуглеводи = 0` і `kcal = 4Б + 9Ж` (норма лишається арифметично цілісною).

**Контрольні вектори (тести 3.2, рік 2026):** `m`, 80 кг, 180 см, 1996, `mid`, `recomp` → BMR 1780, **2480** ккал, Б 144, Ж 64, В 332. `f`, 60 кг, 165 см, 1996, `low`, `recomp` → BMR 1320,25, **1630**, Б 108, Ж 48, В 192. `f`, 150 кг, 150 см, 1946, `low`, `lose_fat` → 2060 за формулою < 4Б+9Ж = 2160 → **2160**, Б 270, Ж 120, В 0.

**Коли рахувати й питати.** Норма створюється **ліниво**: при першому `/yizha` і (мовчки, без питань) при `[✅ Вірно]`, якщо рядків `nutrition_targets` ще немає і профіль повний → рядок `valid_from = сьогодні`, `reason = formula`. Фото й підтвердження **працюють без норми** (показується лише сума). Потрібні: `goal`, `sex`, `birth_year`, `height_cm`, `activity`, вага (профіль або `body_weights`). Анкета 1b дозволяє «Пропустити», тож прогалини реальні. Бракує — `/yizha` не рахує, а ставить **одне** питання про перше відсутнє поле (`goal → sex → birth_year → height_cm → activity → вага`) екранами 1b (`texts.ts`, `onboarding-view.ts`), без нового опитування й без зміни CHECK `onboarding_state`. Екрани 1b не годяться для одного кроку без проходу решти анкети — запасний хід: список бракуючого й `/profil` (**[П]**). Заповнене поле не питається вдруге (P3.2.5).

Профіль змінився → норма **не** перераховується сама (**[П]**): норма — домовленість із датою; змінює її лише тренд (розділ 6). `/yizha` показує «норма від 20.11».

**`/yizha` (3.2)** — підсумок **сьогоднішньої локальної дати**: рядок `З'їдено 1 450 / 2 480 ккал (58 %)`; нижче `Б 98 / 144 г · Ж 40 / 64 г · В 160 / 332 г`; список підтверджених прийомів за день (час за `tz`, позиції, ккал) — не більше 12, далі «…ще N»; рядок `⏳ Не підтверджено: N` (pending за сьогодні, **не в сумі**); перебір — `+120 ккал понад норму`; без норми (бракує полів) — питання вище, суму показуємо. Норма береться **чинна на цю дату** (`getTargetOn`), не найновіша. Текст ≤ 4096 (N6). `yizha` — у `BOT_COMMANDS` («Їжа за день і норма»).

## 4. Потік фото (3.3)

**Вхід.** `message:photo` від власника (білий список — Фаза 0). Файл-картинка (`document` з `image/*`) → «Надішли фото не файлом — так я його розпізнаю». Альбом: кожне фото — окремий прийом і виклик (обмежує ліміт).

**Крок 0 — перевірки до коштів:** немає `ANTHROPIC_API_KEY` → «Розпізнавання ще не підключене» (лог без значення); `aiSpendToday(userId, сьогодні) ≥ AI_DAILY_LIMIT_MICRO` → «Денний ліміт розпізнавання вичерпано. Спробуй завтра» (**клієнт Anthropic не викликається**).

**Робота — у `ctx.waitUntil`** (N2): вебхук одразу 200, `telegramHandler` отримує `ctx`. Дедуп за `update_id` вже стоїть до обробника (Фаза 0): повтор від Telegram не запустить другого виклику. **Один дедлайн 25 с на весь конвеєр** (`AbortController`): `sendChatAction typing` → `getFile` → завантаження → base64 → виклик Anthropic. На платформі `waitUntil` після відповіді живе ≤ 30 с, тож решта (D1, `sendMessage`) має вкластися в ~5 с. Таймаут → «Не встиг розпізнати. Надішли фото ще раз» (N2), у `meals` **0 рядків**, у `ai_usage` — оцінка `FOOD_CALL_EST_MICRO` (запит міг бути оплачений).

**Фото.** Telegram віддає масив `PhotoSize` (стиснуте JPEG, довге ребро ≤ 1280). Беремо **найбільший елемент із `file_size ≤ 2 МБ`**; байти мають починатися з `FF D8 FF`, інакше «Не вдалося прочитати фото». `media_type` = `image/jpeg`. Картинка 1280×960 = ⌈1280/28⌉·⌈960/28⌉ = 1610 візуальних токенів ([vision](https://platform.claude.com/docs/en/build-with-claude/vision), 2026-11-20; ліміти 10 МБ і 8000 px далекі). Власного зменшення немає (немає Images binding). До Anthropic йдуть **base64-байти**; URL файлу Telegram (містить токен) **ніде** не логується й не передається, помилки завантаження — лише статус (N7).

**Підпис-підказка.** `caption` (≤ 300, обрізається; «це 200 г гречки») іде в тезі `<user_caption>` як дані: підпис і текст на самій фото не змінюють правил і формату відповіді.

**Запит.** `@anthropic-ai/sdk` (`1.12.0` за `npm view` 2026-11-20, версія закріплена); `new Anthropic({ apiKey, maxRetries: 0 })` (повтори множать час і кошти); `messages.create({ model: FOOD_MODEL, max_tokens: 1500, output_config: { effort: "low", format: { type: "json_schema", schema } }, system, messages })` — без `temperature`/`top_p`/`prefill`/`tool_choice` (на Sonnet 5.5 це 400); `thinking` не передаємо (глибина — `effort: low`). Сигнал дедлайну — `{ signal }` другим аргументом. У `user`: блок `image` (base64), блок `text` — підпис і **список відомих назв** (`name_uk` усіх `foods`, ≤ 300 штук, ≈ 1 тис. токенів): модель має брати назву дослівно, якщо продукт той самий — частіше збігається аліас. Вимоги до `system` (текст — 3.3, `src/ai/food-prompt.ts`): вага **приготованої страви на тарілці**; значення на 100 г — для того самого стану; назва — однина, називний, українською; ≤ 8 позицій; не їжа → `not_food: true`, `items: []`; невпевненість — у `confidence`, не в грамах.

**JSON-схема** (`additionalProperties: false`; чисельні межі `min/max` структурований вивід не підтримує — їх перевіряє код): `{ not_food: boolean, items: [{ name_uk: string, grams: number, kcal_100: number, protein_100: number, fat_100: number, carbs_100: number, confidence: "low"|"medium"|"high" }] }`, обидва поля `required`.

**Валідація (`parseFoodResponse`, чиста).** Перед розбором: `stop_reason` має бути `end_turn`; `max_tokens` / `refusal` → «не вдалося»; текстовий блок → `JSON.parse` у `try`. Далі: `not_food` або порожній `items` → **NOT_FOOD**; інакше кожна позиція: `name_uk` 1–60 після trim і непорожній `normalizeAlias`; `grams` скінченне 5–2000 (→ ціле); `kcal_100` 0–900; `protein/fat/carbs_100` 0–100 кожне, сума ≤ 100,5; **Атуотер:** `|kcal_100 − (4Б + 4В + 9Ж)| ≤ max(30, 0,3·kcal_100)`; `confidence` з переліку; позицій 1–8. Хоч одна позиція не пройшла → усе **INVALID** («Не вдалося розібрати відповідь. Спробуй ще раз», прийому немає). Межі інклюзивні.

**Зіставлення.** Для кожної позиції `findFoodByAlias(normalizeAlias(name_uk))`. Збіг → беремо **таблицю** (цифри моделі ігноруються). Немає → `insertEstimatedFood` (`source = ai_estimate`, значення моделі × 10, округлені) — ідемпотентно за аліасом: той самий продукт удруге береться з `foods`, нового рядка немає. Далі `createPendingMeal` одним batch (прийом + позиції; `status = pending`, `ai_raw_json`, `ai_model`).

**Не отруювати каталог.** скасування й прострочення `pending` видаляють `meal_items` прийому й **осиротілі** `ai_estimate`-продукти (без жодного `meal_items`) з аліасами: відкинута оцінка не стає еталоном; те саме робить крон для будь-яких осиротілих (збій між створенням продукту й прийому). Підтверджена лишається.

**Повідомлення** (`texts.ts`, HTML, `esc()` на назвах): `🍽 Рис варений ~180 г · 234 ккал`, рядок на позицію (`❓` при `low`, `🆕` для `ai_estimate`), підсумок `Разом: 520 ккал · Б 45 · Ж 12 · В 55` (**сума цілих знімків/розрахунків, округлена один раз**, а не сума округлених), кнопки `[✅ Вірно] [✏️ Грами] [❌ Скасувати]`. Те саме повідомлення редагується далі (`message_id` у `meals`).

**Кнопки** — `callback_data`: `m:y:<id>` · `m:g:<id>` · `m:x:<id>` (префікс `m:` вільний від `o:`, `s:` і дій потоку тренування; тест на унікальність префіксів). Усі дії — лише над прийомом **цього** `userId`.
- **✅ Вірно** → `confirmMeal`: один batch — `UPDATE meals SET status='confirmed' … WHERE id AND user_id AND status='pending'`, потім `UPDATE meal_items SET kcal, protein_dg, fat_dg, carbs_dg` для цього прийому (лише де знімок `NULL`, лише якщо прийом уже `confirmed`), значення `(grams·x_100 + 50) div 100` (ціле, половина вгору). Друге натискання — 0 змін («Вже підтверджено»). Повідомлення змінюється на підсумок із рядком «Сьогодні: 1 450 / 2 480 ккал» (або без норми) і однією кнопкою `[🗑 Скасувати прийом]` (`m:x`) — щоб хибний тап не отруїв день.
- **✏️ Грами** → `await_grams_at = now` (знімає очікування в інших прийомів користувача), знімає `await_input` активного тренування, повідомлення просить: «Надішли грами через пробіл: 200 150» з нумерованим списком позицій.
- **❌ Скасувати** → `cancelMeal`: `pending` → `cancelled` (+ чистка каталогу вище); `confirmed` → `cancelled` (знімок і рядки лишаються для історії, у `dayTotals` не входять). Повторне — без помилки.

**Введення грамів.** Порядок маршрутизації тексту (доповнює `phase-2.md` §2): (1) reply на нагадування про вагу → (2) вага підходу тренування → **(2б) очікування грамів** → (3) анкета → (4) голе число… Очікування діє, якщо є `pending` прийом користувача з `await_grams_at` не старшим за `GRAMS_AWAIT_TTL` (15 хв); команда його знімає. `parseGrams(text, n)` (чиста): розділювачі — пробіл, `,`, `;`, новий рядок; токен `^\d{1,4}(г|g)?$`; значення 0–2000; кількість токенів = числу позицій. `0` = **вилучити позицію** (решта номерів не змінюється); усі нулі — відмова. Помилка → підказка «Очікую 2 числа, отримав 1», очікування лишається. Успіх → `updateMealGrams` (лише власний `pending`), очікування знімається, повідомлення оновлюється.

**Прострочення.** `pending` старший за `MEAL_PENDING_TTL` (24 год від `created_at`): кнопки відповідають «Застаріло — надішли фото ще раз» (перевірка ледача, не залежить від крону) і не змінюють даних; крон у блоці прибирання Фази 1 переводить їх у `cancelled` з чисткою каталогу (`expirePendingMeals`), помилка не зупиняє інших кроків тіку. Підтвердження після 00:00 лягає на `meals.local_date` фото, а не дату тапу.

**Помилки API.** `429`, `5xx`, `overloaded`, обрив → «Сервіс розпізнавання зайнятий, спробуй за хвилину»; `401/403` → «Розпізнавання тимчасово недоступне» + лог без ключа (N9); `400` → як INVALID. Повторів немає. `4xx` не оплачується → у `ai_usage` не пишеться; відповідь `200` пишеться завжди (з `usage`), навіть якщо потім INVALID.

## 6. Корекція норми за трендом (3.4)

Раз на 14 днів код порівнює вагу з цілью й пропонує ±100 ккал. Усе — за локальними датами; вікна `W0` (сьогодні−6…сьогодні) і `W1` (попередні 7) — **ті самі**, що на екранах Фази 2.

**Коли оцінювати.** Крон, для користувача з чинною нормою, у вікні тіків `[09:00, 10:00)` за `tz` (`TREND_LOCAL_MINUTES = 540`, вікно 60 хв, як у Фази 2). Умови, усі разом: (а) `сьогодні − max(valid_from чинної норми, дата останньої пропозиції trend у reminders_sent) ≥ 14`; (б) зважувань у `W0 ∪ W1` **≥ 10**, у кожному вікні **≥ 3**; (в) є пропозиція за порогами нижче. Не виконано (а) або (б) — тихо, без заявки (завтра перевіримо знову); (в) не виконано — теж тихо, цикл не спалюється. Якщо надіслано — заявка `reminders_sent (user, 'trend', дата)` (заявити → надіслати → при помилці зняти, як у Фазі 2).

**Темп:** `p = (avg(W0) − avg(W1)) / avg(W1) · 100` %/тиждень — точною цілочисельною арифметикою (перехресне множення десятих кг, без `float`). Пороги — таблиця `GOAL_BANDS` у `config.ts`: смуга `[lo, hi]` %/тиж; шум середніх за 3–7 зважувань ≈ ±0,25 %, тож додано запас `m = 0,20`:

| `goal` | смуга | `+100 ккал`, якщо `p <` | `−100 ккал`, якщо `p >` |
|---|---|---|---|
| `lose_fat` | −1,0 … −0,5 | −1,20 | −0,30 |
| `recomp` | −0,25 … 0 | **−0,45** | **+0,20** |
| `muscle` | +0,1 … +0,5 | −0,10 | +0,70 |
| `strength`, `health`, `other` | −0,25 … +0,25 | −0,45 | +0,45 |

Межі **строгі**: рівно на порозі — «нічого». Запобіжники: сумарне відхилення від `formula`-норми ≤ ±300 ккал (далі пропозиції немає); нова норма ≥ 1200 ккал. `+100` ккал → вуглеводи +25 г; `−100` → −25 г (вуглеводи ≥ 0; білок і жир не змінюються).

**Повідомлення:** `📈 За 14 днів: 80,0 → 79,4 кг (−0,75 %/тиж) — швидше, ніж треба для цілі. Пропоную 2480 → 2580 ккал (вуглеводи +25 г). [✅ Прийняти] [Ні]`. Кнопки: `n:a:<±100>:<YYYYMMDD>` і `n:d:<YYYYMMDD>` (дельта й дата пропозиції — у даних).

**Прийняття — умовний `INSERT … SELECT … WHERE NOT EXISTS`** одним оператором (атомарно): новий рядок `nutrition_targets` (`valid_from` = сьогодні, `reason = trend`, `source_date` = дата пропозиції, ккал = чинна + дельта) створюється, лише якщо (1) для цієї `source_date` рядка ще немає (частковий UNIQUE) і (2) після дати пропозиції не було ні нового `trend` у `reminders_sent`, ні нового `valid_from` у `nutrition_targets` — інакше «Пропозиція застаріла». Повторне натискання → 0 нових рядків, «Вже застосовано». `[Ні]` лише знімає кнопки; цикл уже обліковано заявкою.
