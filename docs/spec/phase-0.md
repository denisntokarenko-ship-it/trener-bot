# Фаза 0 — Каркас: вебхук, доступ, дедуп

## Задача

Worker приймає апдейти лише від Telegram і лише від власника, кожен апдейт обробляє один раз і відповідає на `/start`. Прод можна забекапити й відкотити до міграції. Це фундамент, на якому фаза 1 записує тренування.

## Схема (міграція фази 0)

**`users`**

| Поле | Тип | Обмеження |
|---|---|---|
| `id` | INTEGER | PK — Telegram ID |
| `first_name` | TEXT | NOT NULL, ≤ 64 символи |
| `tz` | TEXT | NOT NULL DEFAULT `'Europe/Kyiv'` (IANA) |
| `created_at` | INTEGER | NOT NULL, UTC мс |

Поля `training_days`, `remind_time`, `weigh_time` додає міграція фази 2, `sex`, `birth_year`, `height_cm`, `activity` — фази 3 (`ALTER TABLE ADD COLUMN`, див. `decisions.md`).

**`processed_updates`**

| Поле | Тип | Обмеження |
|---|---|---|
| `update_id` | INTEGER | PK |
| `created_at` | INTEGER | NOT NULL, UTC мс; індекс `processed_updates_created_at` (для прибирання у фазі 1) |

## Порядок обробки запиту

1. Метод і шлях: лише `POST /tg/webhook`. Інший шлях → 404, інший метод на цьому шляху → 405. Окремо `GET /health` → 200 `ok` без секрету (для smoke); на `/health` інший метод → 404.
2. Заголовок `X-Telegram-Bot-Api-Secret-Token` порівнюється з `TELEGRAM_WEBHOOK_SECRET` за сталий час. Відсутній чи інший → 401, порожнє тіло.
3. Тіло — JSON `Update`. Не розібралось або немає `update_id` → 200, нічого не записано.
4. Відправник: `message.from.id` або `callback_query.from.id`. Немає відправника, його ID не в білому списку або чат не приватний (`message.chat.type` чи `callback_query.message.chat.type` ≠ `private`) → 200, тиша: відповідь у групу показала б дані власника іншим.
5. Дедуп: `INSERT INTO processed_updates … ON CONFLICT DO NOTHING`. Вставлено 0 рядків → 200, обробник не викликається.
6. Обробник. Виняток → лог (N9), 200; рядок дедупу лишається.

Кроки 1–4 не пишуть у БД і не викликають Telegram API.

## Історії

### P1.1 — Вебхук приймає лише Telegram

**Навіщо:** URL Worker'а публічний; без секрету будь-хто підробить апдейт від імені власника.
**Незалежно тестована:** запити до Worker'а в pool workers з різними заголовками, лічильник рядків у D1.

1. **Given** запит `POST /tg/webhook` без заголовка секрету, **When** Worker його обробляє, **Then** відповідь 401, у `users` і `processed_updates` 0 нових рядків, жодного виклику Telegram API.
2. **Given** заголовок із неправильним секретом (зокрема того самого розміру й з тим самим префіксом), **When** запит, **Then** 401 і 0 записів.
3. **Given** правильний секрет і валідний апдейт від власника, **When** запит, **Then** 200.
4. **Given** правильний секрет, **When** `POST /tg/other` або `GET /`, **Then** 404; **When** `GET /tg/webhook`, **Then** 405.
5. **Given** правильний секрет і тіло `not json`, **When** запит, **Then** 200 і 0 записів.

### P1.2 — Білий список

**Навіщо:** бот особистий; чужий не повинен ні отримати відповідь, ні залишити слід у БД.
**Незалежно тестована:** фейкові апдейти з правильним секретом і різними `from.id`.

1. **Given** `ALLOWED_TELEGRAM_IDS = "111, 222"`, **When** приходить `/start` від `333`, **Then** 200, жодного `sendMessage`, 0 рядків у `users` і в `processed_updates`.
2. **Given** той самий список, **When** `callback_query` від `333`, **Then** 200, `answerCallbackQuery` не викликається, 0 записів.
3. **Given** список із пробілами навколо ID, **When** `/start` від `222`, **Then** апдейт обробляється (пробіли обрізаються).
4. **Given** `ALLOWED_TELEGRAM_IDS` порожній або не заданий, **When** `/start` від будь-кого, **Then** 200, тиша, 0 записів.
5. **Given** апдейт без відправника (`channel_post`, `my_chat_member` без `from`), **When** запит, **Then** 200, 0 записів.
6. **Given** власник із білого списку пише `/start` у груповому чаті (`chat.type = "group"` або `"supergroup"`), **When** запит, **Then** 200, жодного `sendMessage`, 0 записів у `users` і `processed_updates`.

### P1.3 — Апдейт обробляється один раз

**Навіщо:** Telegram повторює доставку, якщо не отримав 200 вчасно; повтор не має дублювати повідомлення чи записи.
**Незалежно тестована:** той самий JSON двічі, шпигун на обробнику.

1. **Given** апдейт `update_id = 1000` від власника, **When** він надходить двічі, **Then** обробник викликано рівно один раз, у `processed_updates` один рядок, обидві відповіді 200.
2. **Given** два різні `update_id` з однаковим текстом, **When** надходять, **Then** обробник викликано двічі.
3. **Given** обробник кидає виняток на `update_id = 1001`, **When** Telegram повторює `1001`, **Then** обробник не викликається вдруге (at-most-once, `decisions.md`), обидві відповіді 200.
4. **Given** апдейт від чужого ID (P1.2), **When** він надходить, **Then** рядка дедупу немає — дедуп іде після білого списку.

### P1.4 — `/start`

**Навіщо:** перша перевірка, що весь ланцюжок живий, і точка створення профілю.
**Незалежно тестована:** апдейт `/start`, мок Telegram API через `fetch`, рядки `users`.

1. **Given** власника `111` ще немає в `users`, **When** він надсилає `/start`, **Then** з'являється рядок `id = 111`, `first_name` з апдейту, `tz = 'Europe/Kyiv'`, `created_at` = час обробки; бот відповідає привітанням.
2. **Given** рядок `111` уже є з `tz = 'Europe/Warsaw'`, **When** `/start` з іншим `first_name`, **Then** рядок один, `first_name` оновлено, `tz` і `created_at` не змінені.
3. **Given** власника немає в `users`, **When** його перший апдейт — будь-який інший текст, **Then** рядок `users` створюється так само (профіль — від першого апдейту власника, не лише від `/start`).
4. **Given** фаза 0, **When** власник надсилає не-команду, **Then** відповідь «Поки що я вмію лише /start.» (фаза 1 замінює).

Текст привітання: `Привіт, {first_name}! Я записую твої тренування.` + список команд, доступних у поточному релізі, по одній на рядок.

### P2.1 — `set-webhook`

**Навіщо:** реєстрація вебхука — повторювана ручна дія з секретом; скрипт робить її однаково й не світить токен.
**Незалежно тестована:** запуск з мокнутим `fetch` до `api.telegram.org`.

1. **Given** у середовищі процесу `TELEGRAM_BOT_TOKEN`, `TELEGRAM_WEBHOOK_SECRET`, `WORKER_URL`, **When** людина запускає `npm run set-webhook -- preview`, **Then** скрипт викликає `setWebhook` з `url = {WORKER_URL}/tg/webhook`, `secret_token`, `allowed_updates = ["message","callback_query"]`, `max_connections = 1`, `drop_pending_updates = false`; далі `getWebhookInfo` і `getMe` і друкує лише середовище з аргументу, `@username` бота, хост URL, `pending_update_count`, `last_error_message`. Аргумент лише підписує вивід — змінні середовища ті самі; за `@username` людина бачить, якого бота оновила.
2. **Given** вебхук уже встановлено, **When** скрипт запускають удруге, **Then** стан той самий, код виходу 0.
3. **Given** не задана одна зі змінних, **When** запуск, **Then** код виходу 1 і назва змінної (без значень інших); жодного запиту до Telegram.
4. **Given** аргумент не `preview` і не `production`, **When** запуск, **Then** код виходу 1.
5. **Given** будь-який запуск, **When** перехоплено stdout і stderr, **Then** у них немає ні токена, ні секрету.

### P2.2 — Бекап прода й відкат міграції

**Навіщо:** Time Travel тримає лише 7 днів, а міграція може зламати дані; перед кожною міграцією прода потрібен файл і відомий спосіб повернутися.
**Незалежно тестована:** репетиція на preview.

1. **Given** D1 середовища існує, **When** `npm run backup:prod`, **Then** з'являється `backups/prod-YYYYMMDD-HHMMSS.sql` (UTC), непорожній, з `CREATE TABLE` для кожної таблиці; код виходу 0.
2. **Given** export впав, **When** скрипт завершується, **Then** код виходу ≠ 0, недописаний файл видалено.
3. **Given** файл у `backups/`, **When** `git check-ignore backups/<файл>`, **Then** файл ігнорується.
4. **Given** чек-лист «міграція прода» в `docs/RUNBOOK.md`, **When** людина його виконує, **Then** кроки йдуть у порядку: `backup:prod` → `wrangler d1 time-travel info … --env production` (записати bookmark) → `migrations apply --remote` → smoke `/start` → за збою `wrangler d1 time-travel restore … --bookmark=<записаний>`.
5. **Given** репетиція на preview: рядок X є, bookmark записано, потім X змінено, **When** `time-travel restore` на bookmark, **Then** X як до зміни. Restore відкочує й дані, записані після bookmark, — RUNBOOK про це попереджає.
6. **Given** відкат потрібен пізніше ніж за 7 днів, **When** людина читає RUNBOOK, **Then** там є шлях: імпорт SQL-файлу з `backups/` у нову D1 і перемикання `database_id`.

### P2.3 — Замір CPU

**Навіщо:** N1 — головна ціна вибору Workers; її треба підтвердити цифрою до фази 1, а не припущенням.
**Незалежно тестована:** `wrangler tail --env preview --format json` у файл.

1. **Given** preview задеплоєно й вебхук встановлено, **When** надіслано ≥ 10 `/start` від власника й ≥ 10 фейкових апдейтів від чужого ID (curl з правильним секретом), **Then** медіана й максимум `cpuTime` кожної групи записані в «Рішення» `docs/PROGRESS.md`.
2. **Given** медіана `/start` > 5 мс, **When** замір завершено, **Then** робота зупиняється з пропозицією тонкого клієнта на `fetch` замість grammY.

## Поза межами

- Будь-які команди, крім `/start` — фаза 1+.
- Групи — крок 4 відсікає не-приватні чати (`allowed_updates` фільтрує типи апдейтів, а не чати).
- Канали, inline-режим, `edited_message` — `allowed_updates` їх не просить.
- Онбординг інших людей — білий список заміняє реєстрацію до «Після MVP».
- Rate limiting — для одного власника за білим списком не потрібен.
- Прибирання `processed_updates` — крон фази 1.
- CI, lint, typecheck — завдання 0.3, не історії спеки.

## Невідоме

- `[ПОТРІБНО УТОЧНИТИ: адреса Worker'а — *.workers.dev чи власний домен]` — неблокуюче; припущення: `*.workers.dev`, значення — у `WORKER_URL`.
- Другого Telegram-акаунта для перевірки «чужого» немає — не блокує: чужий ID перевіряється фейковим апдейтом через curl з правильним секретом.
